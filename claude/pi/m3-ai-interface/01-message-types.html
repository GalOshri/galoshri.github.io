LLM · Thinking content

Modern models can "reason" before answering — generating a private chain of thought that improves hard answers. Providers expose it as a distinct content type so clients can display it dimmed, hide it, or bill it separately (thinking tokens cost output-token prices!).

The odd fields make sense once you know the round-trip rules: providers require thinking blocks to be sent back in later turns (so the model can build on its own reasoning), and they sign the content — thinkingSignature — to detect tampering. When safety filters redact the text, the encrypted payload still travels in the signature field with redacted: true, preserving multi-turn continuity. Fields like these are fossils of real provider constraints; typed models like this one teach you the API's true shape better than the docs do.

The three messages

Read the content types closely — they encode who may say what:

  • Users send text and images. Never tool calls — you can't fake the model asking for something.
  • Assistants produce text, thinking, and tool calls. Never images (that's a separate image-generation world).
  • Tool results return text and images (a screenshot tool!), tied back by toolCallId, flagged by isError.

Impossible states are simply unrepresentable. In Python you'd write a validator and a docstring; here the compiler is the validator. Notice too that AssistantMessage is self-documenting about its origin — it permanently records which api/provider/model produced it and what it cost (usage). Five ways a response can end: naturally, out of room, wanting tools, broken, or cancelled. You've already watched the agent loop branch on three of them. Note that "error" is a value here, not an exception type — the errors-as-data philosophy is baked into the vocabulary itself.

TypeScript · Union types and structural typing

string | (TextContent | ImageContent)[] reads inside-out like Python's Union[str, list[Union[TextContent, ImageContent]]]: a value that is one of several types. TypeScript makes unions cheap and ubiquitous — even string literals form types, which is how StopReason can be "one of these five exact strings" with zero runtime machinery. (Compare Python, where you'd reach for an Enum class.)

The second idea is structural typing: a value satisfies UserMessage if it has the right fields, period. Nothing is ever "an instance of" UserMessage — no class exists, no constructor ran. Any object literal, JSON from disk, or network payload with role: "user", valid content, and a timestamp is a UserMessage. Python's Protocol is the same idea (duck typing, formalized); here it's the default for everything. That's why session files (lesson 2.7) can be parsed straight back into typed messages — the types describe data, not objects.

Why this vocabulary is the whole ballgame

Every provider speaks a different dialect: Anthropic nests content blocks one way, OpenAI another, Google a third; tool calls appear in three incompatible formats. pi's answer is this normalized vocabulary: the rest of the system speaks only these types, and each provider adapter (Module 4) translates to and from its dialect at the edge. That's what "unified LLM API" means concretely — the union of everyone's concepts, with the differences confined to files you rarely read.
