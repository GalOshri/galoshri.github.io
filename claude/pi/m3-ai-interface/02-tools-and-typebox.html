Tools and TypeBox

A tool definition has to satisfy three different consumers: the TypeScript compiler, a runtime validator, and a language model reading JSON Schema. pi makes one definition serve all three. This lesson unpacks the trick — and the Context type that carries everything to the wire.

The Tool type is suspiciously small

Name, description, parameters — that's a tool, as far as pi-ai is concerned. No execute function! At this layer a tool is only a description sent to the model; executing is the agent layer's business (Module 5 adds AgentTool with the execute method). The layering from Module 1 again, visible in a type.

And there's Context — the entire request, the exact three-field object you watched streamAssistantResponse build in lesson 2.4. Everything a model ever learns arrives through one of these three fields.

The interesting part: parameters

The parameters field holds a TypeBox schema. Recall the read tool's, from lesson 2.5:

This one declaration is doing three jobs simultaneously:

  • For the model: readSchema is a runtime object that serializes to standard JSON Schema — {"type":"object","properties":{"path":{"type":"string","description":"Path to…"}}} — which is exactly what provider APIs expect in their tools field. Even the description strings are prompt engineering: they're the model's documentation for each parameter.
  • For the validator: when a tool call comes back, pi checks its arguments against this same object (validateToolArguments, called inside the agent loop) — catching the model inventing parameters or passing a string where a number belongs, before any tool code runs.
  • For the compiler: the last line is the magic. Static<typeof readSchema> asks TypeScript to compute, at compile time, the type that the schema describes: { path: string; offset?: number; limit?: number }. The tool's execute function is typed with it, so schema and implementation can never drift apart — change one, and the other stops compiling.

TypeScript · TypeBox ≈ pydantic (and generics)

Remember that TypeScript types are erased at runtime (lesson 1.3) — so they can't validate network data. TypeBox fills the gap from the other direction: you build a value (a JSON Schema object) and derive the static type from it. Python's pydantic is the same bargain reversed — there you write a class and derive the schema. One source of truth, both worlds served.

This is also your first proper look at generics. Tool<TParameters extends TSchema> is Generic[T] with a constraint: any particular tool can be precise (Tool<typeof readSchema>), while code that handles "any tool" writes plain Tool and gets the default. The extends clause means "T must at least be a schema" — Python's TypeVar("T", bound=TSchema). You'll see this pattern constantly: a container type, one type parameter, a constraint.

Note · descriptions are behavior

Because the model chooses tools by reading these descriptions, editing a description changes the agent's behavior as surely as editing code. When pi's maintainers tune when the model reaches for grep versus read, they're often editing prose inside Type.String({ description: ... }). Prompt engineering hides in type definitions.

What you now know
