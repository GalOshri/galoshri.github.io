Retries and error classification

LLM providers fail constantly — overloaded, rate-limited, mid-stream disconnects. The difference between an agent that shrugs and one that dies is knowing which failures to retry. pi's answer is a deliberately humble file: two regexes and a comment explaining what it refuses to do.

Classify, don't decide

Note the input type: an AssistantMessage. Because errors are values (lesson 3.6), the classifier examines a message, not an exception. And note the doc comment drawing a boundary: this function classifies; the retry policy — how many attempts, what backoff, what to show the user — belongs to the caller. The coding agent's session layer supplies that policy with user-visible countdowns; a headless deployment might choose differently. Mechanism here, policy up there: layering applied to failure handling.

Two classifications deserve a second look. "stream ended before message_stop": remember the Anthropic adapter tracking sawMessageEnd? A connection that dies mid-generation surfaces as this error — and it's retryable, because the death was the network's, not your request's. And "billing" as non-retryable: an agent that auto-retried a billing failure in a loop would hammer a dead account forever. The expensive mistakes sit on the never-retry list.

Note · where the policy lives

Upstairs, the coding agent wraps its stream function with the policy: on a failed message, first check context overflow (a different problem with a different cure — compaction), then consult this classifier, then retry with backoff while telling you it's doing so — that "Retrying in 8s (attempt 2/5)…" line in pi's footer. Same classifier, any policy. You'll see the wiring in lesson 6.2.

Engineering · The retry discipline

Three rules, all visible in this design. Classify before you retry — blind retries amplify outages and drain wallets; the transient/permanent split is the load-bearing decision. Back off exponentially — wait 1s, 2s, 4s… so a thousand failing clients don't synchronize into a stampede (the policy layer's job here). Keep the budget visible — retries hide problems; pi surfaces each attempt in the UI rather than silently stalling. And a fourth, implicit: retrying is only safe because a failed assistant turn is restartable — the conversation state it consumed is still in memory, unchanged. Know what your system can replay before you replay it.
