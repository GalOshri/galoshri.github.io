The layered architecture

You've seen that pi's five packages form a straight dependency line. This lesson is about why that line is the most important design decision in the repository — and how to verify architectural claims like this one yourself, from the code, rather than taking documentation on faith.

The rule: dependencies point one way

Spelled out, the contract is:

  • pi-tui knows how to render text and read keystrokes. It contains the word "terminal" thousands of times and the word "model" zero times. You could use it to build a terminal Tetris.
  • pi-ai knows how to send messages to LLM providers and stream responses back. It has no concept of an agent, a tool executing, or a screen. You could use it to build a chatbot with no loop at all.
  • pi-agent-core knows the loop: send context, collect tool calls, execute, repeat. It doesn't know the tools are about coding — it would run a cooking agent just as happily. And it has no user interface whatsoever.
  • pi-coding-agent is where it all becomes a product: coding tools (read/edit/bash), a terminal chat UI, session files, settings. It writes almost no fundamentals itself — it composes the three layers below.

No pi-tui, no pi-coding-agent — the loop literally cannot mention a screen or a coding tool, because nothing of the sort is in scope. Meanwhile pi-tui's own manifest lists exactly two external dependencies — a Markdown parser and a Unicode-width table — and zero internal ones. The architecture isn't a promise; it's mechanically enforced by what each package is allowed to import.

Engineering · Dependency direction and layering

The deepest idea in large-scale code organization: stable things should not depend on volatile things. "What a message is" changes rarely; "how the footer looks" changes weekly. By forcing all arrows to point from volatile (product) to stable (primitives), a change at the top can never break the bottom, and each lower layer can be understood, tested, and reused in isolation.

The classic smell to watch for is the cycle: A imports B and B imports A, which means neither can be understood alone and they're really one tangled unit. Python projects fight the same battle with circular import errors — the difference here is that the package boundary makes the layering physical. packages/tui could not import the agent even by accident; npm wouldn't resolve it.

What the layering buys, concretely

Three real payoffs you'll witness during this course:

  • Reuse. The same pi-agent-core that powers this terminal app also powers pi-chat, the team's separate Slack-automation project. No UI in the loop means any UI can be bolted on — including "no UI at all," which is exactly what pi's headless RPC mode is (Module 10).
  • Testability. Because pi-ai hides all providers behind one interface, the test suite swaps in a scripted fake provider (the "faux" provider, Module 4) and tests the entire agent stack without network calls or API bills.
  • Learnability. This one benefits you directly. Each module of this course studies one layer while treating the layer below as a solved black box. That's not a teaching simplification — it's genuinely how the code is built, and how professionals navigate any large system: pick a layer, trust its neighbors' contracts.

Where the seams show

Real codebases are never perfectly clean, and honest reading means noticing the seams. Two you'll meet later: pi-agent-core ships a "batteries included" harness layer that the coding agent ignores, preferring to hand-wire its own (the plot twist of Module 5); and the coding agent's interactive mode is a single 5,800-line file that composition didn't save from growing huge (Module 6 turns reading such files into a skill). Layering constrains where mess can live; it doesn't abolish mess.

What you now know

pi is four one-way layers plus an experiment on top. When you're lost at any point in this course, come back to one question: which layer am I in, and what does it import?
