A tour of the monorepo

pi's source is one Git repository containing five separately published packages. Before reading any code, it pays to know where everything lives and how the pieces are stitched together — because that stitching is itself a big-codebase skill.

One repo, five packages

Open the repository root and you see a thin shell — configuration, scripts, docs — around a single important directory: packages/.

This arrangement is called a monorepo: multiple packages, versioned and developed together in one repository, but published to the npm registry as five independent installable units. Someone who only wants the LLM API can npm install @earendil-works/pi-ai and never touch the rest.

Node.js · package.json and npm workspaces

Every Node package has a package.json — the equivalent of Python's pyproject.toml. It declares the package's name, version, dependencies, and runnable scripts (npm run build ≈ a Makefile target).

A workspace root is a package.json with a "workspaces" list. Running npm install there installs dependencies for all listed packages at once and — crucially — symlinks the sibling packages into each other. When coding-agent imports @earendil-works/pi-ai, npm resolves it to the local packages/ai folder, not the registry. Edit the library, and the app sees it immediately. Python's closest analogue is pip install -e for several local packages, or uv workspaces.

Two details in that file are worth savoring. First, "private": true — the root itself is never published; it exists only to coordinate. Second, look at the build script: no clever build orchestrator, just cd into each package in a fixed order and build it. Read it like a checklist:

  • Name and version. The @earendil-works/ prefix is an npm scope — a namespace, like a GitHub org. Notice the version: 0.80.3. Every package in the repo carries the same version, bumped together on every release ("lockstep versioning"). It sacrifices per-package version meaning for a huge simplification: any combination of pi packages with matching versions is known to work together.
  • Source vs. build output. TypeScript in src/ is compiled to plain JavaScript in dist/, and "main" points consumers at the compiled output. You read src/; Node runs dist/.
  • Dependencies. The internal dependency (pi-ai) tracks the lockstep version. The three external ones are pinned to exact versions — no ^, no ranges. That's a deliberate security posture we'll dig into in lesson 5.
  • Only three external dependencies. For a package this central, that is strikingly few. pi builds most things itself — which is precisely why it's such a good codebase to learn from.

What you now know

A monorepo is not a pile of code; it's a dependency graph made visible. pi's graph is a straight line — tui and ai at the bottom, the product at the top — and that single fact will organize everything else you learn about it. Next: the language all of this is written in, decoded for Python eyes.
