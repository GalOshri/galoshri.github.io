Keyboard input, part 1: raw mode

Output was half the story. Input is the murkier half: keystrokes reach a program as an undifferentiated stream of bytes, batched unpredictably, with paste and typing indistinguishable — unless you negotiate. This lesson covers the plumbing from raw bytes to clean per-key events.

Entering raw mode (with an exit plan)

The moves, in order: remember the old state (a TUI that crashes without restoring cooked mode leaves the user's shell unusable — the classic "my terminal is broken" bug); flip to raw so every keypress arrives immediately, unbuffered, unechoed; then negotiate upgrades with the terminal — bracketed paste, Windows VT input, and the Kitty protocol (next lesson). Note that negotiation is literally writing escape codes to stdout and listening for the terminal's escape-code replies on stdin: the terminal is a peer you talk to, not a device you configure.

The batching problem, and StdinBuffer

Raw mode's catch: bytes arrive in arbitrary chunks. Type fast and one data event carries "abc"; an arrow key is the three bytes \x1b[A which may arrive split across two events; and a paste is one giant blob you must not interpret as typed commands (imagine pasting text containing q into something that quits on q…).

StdinBuffer (434 lines) is the fix — a small state machine that reassembles and splits the stream into one event per logical sequence: single keys, complete escape sequences, and paste blocks (delimited by the bracketed-paste markers we enabled above) emitted whole as a separate paste event. The 10ms timeout handles the genuinely ambiguous case: a lone \x1b might be the Escape key or the start of a longer sequence still in flight — wait a beat, then decide. Reassembly-with-timeout is the same shape as the SSE line-buffering you read in lesson 4.2; byte streams always need this dance.

Node.js · EventEmitter

StdinBuffer extends EventEmitter — Node's built-in pub/sub base class and the ancestral pattern of the platform. Mechanically it's a dict of listener lists: emitter.on("data", fn) appends, emitter.emit("data", seq) calls each listener synchronously. Python's closest kin are signal libraries (blinker) or hand-rolled callback lists; Node bakes it into the core (streams, sockets, and processes all are EventEmitters — you used one in lesson 6.5: child.stdout.on("data")).

Modern typed twist: EventEmitter<StdinBufferEventMap> — a generic event map so on("data", ...) and on("paste", ...) have typed payloads and a typo'd event name fails the build. Compare this to pi's other pub/sub, the Agent's awaited listeners (5.4): EventEmitter is synchronous fire-and-forget, fine for keystrokes; the Agent needed ordering and settlement guarantees, so it rolled its own. Choosing between those two is a recurring design decision, and now you've seen both sides of it in one codebase.

The routing chain

From TUI.handleInput, each clean sequence runs a gauntlet: terminal-protocol responses are consumed first (color queries, protocol negotiation — invisible housekeeping), then global input listeners get a veto (extensions can consume or rewrite input — lesson 8.1's input event), then the overlay stack (an open dialog captures keys before the world below), and finally the focused component's handleInput(data) — usually the editor. After any input, requestRender(). Notice there's no global keymap dispatching to actions; components interpret their own bytes, with a shared matchesKey helper for decoding. Which raises the question of how you match "ctrl+shift+p" against bytes at all — next lesson.

What you now know

Input = raw mode with a restore plan, negotiated terminal upgrades, a reassembly state machine turning byte soup into per-sequence events, and a priority chain from protocol housekeeping down to the focused component. The remaining mystery is the bytes themselves — why ctrl+shift+p needs a protocol upgrade to even exist.
