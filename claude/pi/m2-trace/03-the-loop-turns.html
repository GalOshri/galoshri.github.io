Reading it as a story

For our traced message, the story will be short:

  • Turn 1. The conversation (system prompt + your one user message) goes to the model. The model replies: "I should look at the file" — a reply containing a tool call. The loop runs the read tool, appends the result to the conversation, and turns again.
  • Turn 2. The conversation — now user message, assistant tool-call, tool result — goes to the model again, in full (remember: the model is stateless). This time it replies with prose. No tool calls → hasMoreToolCalls = false → inner loop exits.
  • Epilogue. You haven't typed anything meanwhile, so the follow-up queue is empty and the outer loop breaks. agent_end.

Notice the two queues getting drained at the seams. Steering messages slip in between turns — that's what happens when you type while pi works, and why it reacts to mid-task corrections without restarting. Follow-ups wait politely until the agent would stop. The queues themselves live in the Agent class from last lesson; the loop just polls them at the right moments.

And notice what the loop does not contain: no UI, no file paths, no provider names, no persistence. It receives a config full of functions (getSteeringMessages, convertToLlm, the tools themselves) and calls them at the right times. That's dependency injection without the framework — and it's why this same loop can power a terminal app, a Slack bot, or a test harness.

Node.js · async/await, and where the parallelism isn't

Every interesting line here says await: the code pauses at that point until a slow operation (a network response, a file read) completes, without freezing the program — other work, like repainting the screen, proceeds meanwhile. If you know Python's asyncio, this is the same async def/await idea with one glorious simplification: there is no event-loop bookkeeping. No asyncio.run(), no "am I in a loop?" errors. JavaScript runtimes have exactly one event loop, always running; every program is async by birth.

One thing async does not give you is parallel CPU work — JavaScript is single-threaded, like Python-with-GIL but stricter. Concurrency here means overlapping waits, which is perfect for an agent: it's almost always waiting on a model or a subprocess. An async function returns a Promise — Python's Future, near enough — and await unwraps it. We'll open Promises properly in Module 3.

What's the emit(...) on every other line?

That's the broadcast channel from last lesson. The loop is handed an emit function; every lifecycle moment (turn_end, message_start…) is announced through it, and the Agent class fans each event out to subscribers and waits for them before proceeding. That little await emit(...) hides a strong guarantee: the UI and the session log are never behind the loop. Module 5 examines why that's worth its costs.

What you now know

The agent is two nested while loops: the inner one turns as long as the model requests tools (feeding results back into the conversation), the outer one restarts for queued follow-ups.
