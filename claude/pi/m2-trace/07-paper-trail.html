The paper trail

One subscriber to the agent's broadcast hasn't had its moment yet: the session logger. Everything that just happened — your question, the tool call, the answer — was also written, as it happened, to a file. Close the terminal, come back tomorrow, run pi again: the conversation resumes. This lesson reads that file.

Where conversations live

One file per conversation, grouped into directories by the project you ran pi in (the working directory, with slashes turned into dashes). The extension is the story: .jsonl — JSON Lines.

Three observations, in ascending order of cleverness:

  • It's the conversation, verbatim. The same message objects you watched move through memory in lessons 2.2–2.5, serialized. Resuming a session is just reading the file back into the array. Even token usage is preserved — this file is also pi's cost ledger.
  • Each line is written the moment its event fires. The session manager listens for message_end on the broadcast channel and appends one line. If pi crashes mid-conversation, the file is valid up to the last completed message; nothing needs recovery.
  • Every entry has an id and a parentId. Why would a linear log need parent pointers? Because it isn't linear — it's a tree. Rewind the conversation and take a different path, and pi appends new entries whose parentId points at the fork point. Old branches stay in the file; the "current" conversation is whatever path leads to the active leaf. Undo, forking, and branch comparison all fall out of this one field. (Module 7 explores it.)

Engineering · JSONL and append-only logs

JSON Lines — one complete JSON object per line — is what you reach for when you want structure and the virtues of a plain log: append a record with an ordinary file write, read with for line in file: json.loads(line), inspect with grep, truncate safely at any newline.

Append-only is the deeper discipline: never rewrite what's written; represent change as new entries (like pi's fork-by-parentId). You lose the ability to "edit history" and gain crash-safety, a full audit trail, and trivially correct concurrent readers. Databases build their write-ahead logs this way; Git's object store, Kafka, and accounting ledgers are all the same idea. When you see id/parentId in a log, you're looking at a persistent tree grown by appending — one of the most reusable ideas you'll take from this course.
