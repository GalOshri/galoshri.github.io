Talking to the model

Inside the loop sits one function where the conversation leaves the process and crosses the network: streamAssistantResponse. This is also the border crossing between the agent layer and pi-ai — and where "the model is typing…" becomes a real, visible mechanism.

Packing the bags: building the LLM context

Two preprocessing hooks before anything is sent. transformContext lets the app prune or rewrite the conversation (the coding agent uses this for compaction, Module 7). Then convertToLlm translates the agent's richer message vocabulary down to what a model API understands — the coding agent has custom message types (bash executions you ran yourself, extension messages) that get converted or dropped here. The comment in the source says it plainly: this is the only place that translation happens.

The whole request is three fields: system prompt (standing instructions — Module 7 shows pi's), messages (the entire conversation, every time), and tools (descriptions of what the model may ask for — next lesson). The API key is resolved fresh each call because subscription tokens expire mid-session. Then one call into pi-ai: streamFunction, by default streamSimple, which speaks the right wire protocol for whatever config.model is — Anthropic, OpenAI, Google, or 32 other providers. The loop neither knows nor cares which.

LLM · Streaming, and why it isn't cosmetic

A model generates text one token (word-fragment) at a time; a long answer can take a minute. Providers therefore offer streaming APIs: instead of one response at the end, you receive a live feed of fragments as they're generated. For a chat UI that's nice — you watch the answer type itself. For an agent it's essential: pi can show a tool call forming, start a spinner, or let you abort a doomed response seconds in, rather than paying for a full wrong answer. The underlying wire format (Server-Sent Events) is Module 4's subject; what reaches this function has already been normalized.

What does streamSimple return? Not the reply — a stream of events about the reply being born. The second half of the function consumes it:

Recognize the pattern from lesson 2.2? Another discriminated union, another switch on .type. Two clever details:

  • Every event carries partial — a complete snapshot of the assistant message so far. Consumers never assemble fragments themselves; they always hold a valid message that simply keeps growing. The half-born message even sits in the conversation array already, replaced wholesale on each event.
  • Errors arrive as events, not exceptions. The error case is handled in the same switch, and the loop above reacts to stopReason === "error" on an ordinary message. Network failures are data, not control flow — a design rule enforced across all of pi-ai (lesson 3.6 shows how).

Node.js · Async iterators and for await

for await (const event of response) is Python's async for event in response. The object being looped over is an async iterable: each iteration awaits the next value, so the loop body runs when data arrives and sleeps in between. It's the natural shape for "a sequence that trickles in over time" — streaming tokens, lines from a subprocess, rows from a slow query.

Just as Python has generators (yield) to produce such sequences, JavaScript has async function*. pi actually hand-rolls its stream object instead of using a generator — a push-queue called EventStream with a bonus result() promise for "just give me the final message" (you can see it used in the done case above). Lesson 3.5 builds it from scratch.

Meanwhile, on your screen

Follow one keypress-worth of model output all the way now: a token arrives over the network → the adapter parses it → text_delta event → this switch updates partialMessage → message_update goes out on the broadcast channel → the UI subscriber updates a component → the renderer repaints one line of your terminal (lesson 2.6). That entire pipeline runs perhaps fifty times a second while the model "types." Nothing anywhere blocks; it's await all the way down.
