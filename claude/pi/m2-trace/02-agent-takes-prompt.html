LLM · Messages, roles, and the conversation-as-list

Every modern LLM API sees a conversation the same way: a list of messages, each tagged with a role. user messages are yours; assistant messages are the model's; tool results get a role of their own. The model itself is stateless — it remembers nothing between calls. Each time you "continue" a conversation, the client sends the entire list again and the model predicts what an assistant would say next.

Grasp that and several mysteries dissolve at once: why long chats get slow and expensive (the list grows), why "context windows" run out (the list has a maximum size), and why pi will later need compaction (Module 7) to shrink the list gracefully. The conversation is just an array — and pi's whole job is curating what's in it. Note content is itself a list of typed blocks (text, images…) rather than one string; that structure pays off two lessons from now.

Also note what prompt() does if a run is already active: it refuses, pointing you at steer() and followUp() — queues for injecting messages into a running agent. File that away; it's how typing while pi is working actually works (Module 5).

How the UI finds out: events

prompt() starts the loop (next lesson), but notice the return type: Promise<void>. It hands back nothing. The screen can't be updated from a return value that doesn't exist — so how does the UI know what's happening? It subscribes. Anyone can register a listener, and the Agent narrates its life as a stream of typed events:

Read it as a radio broadcast schedule: a run starts (agent_start), then for each turn you hear the assistant's message being born (message_start), growing word by word (message_update), finishing (message_end), tools running (tool_execution_*), the turn closing (turn_end) — until agent_end signs off. The interactive UI is one subscriber. The session's disk-writer is another. They don't know about each other.

TypeScript · Discriminated unions

That AgentEvent type is a discriminated union: a set of alternative object shapes, each carrying a literal type field (the discriminant) that says which shape it is. The pipe | means "one of these."

The magic is in how you consume one. Write switch (event.type) and inside case "turn_end": the compiler knows event has a toolResults field — and that it doesn't in case "agent_start":. Python's closest analogue is match over a union of dataclasses, but here the narrowing is compile-time-checked: touch a field that doesn't exist in that branch and the build fails. This is the idiom of this codebase. Messages, streaming chunks, session entries, UI events — all discriminated unions. Learn to read one and you can read half of pi.
