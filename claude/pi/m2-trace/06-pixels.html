Streaming to your terminal

While the loop turned, your screen was alive: a spinner, then words appearing mid-sentence, a nicely boxed tool call, syntax-highlighted file contents. Time to meet the layer that painted all that — pi-tui — at flyover altitude.

A UI framework where everything is lines of text

Browsers give you HTML and CSS; a terminal gives you a grid of character cells and some escape codes. pi-tui builds a component system on top of that grid, and its central interface is startlingly small:

That's the whole contract: given a width, return an array of strings — one per terminal line. A chat message is a component. The spinner is a component. The editor you typed into is a component. The screen is a list of components, and rendering is: ask each for its lines, concatenate the arrays. If you've used React, squint: render() returning lines instead of virtual DOM, invalidate() instead of re-render triggers. Same philosophy, one-thousandth the machinery.

From agent event to changed lines

The interactive mode subscribed to the Agent's broadcast back in lesson 2.2. Its listener maps events to component updates — conceptually:

  • message_start (assistant) → create a message component, append to the chat list
  • message_update → hand the component the new partial text; it re-renders its Markdown
  • tool_execution_start → add a tool-call component with a spinner
  • tool_execution_end → swap the spinner for the result (diff view, file listing…)

Each update marks the tree dirty and requests a render. Fifty message_updates a second would mean fifty full repaints — so requests are coalesced and capped at roughly sixty frames a second, like a game loop.

The differential renderer

Here's the part that makes pi feel instant. Repainting a terminal from scratch — clear everything, reprint every line — flickers and, over SSH, crawls. So the renderer keeps a copy of what it drew last time (previousLines) and compares:

The renderer finds the first changed line and the last changed line, moves the terminal cursor up to the first, and rewrites just that window — wrapping the whole update in a "synchronized output" escape sequence so the terminal applies it atomically, without flicker. When the model is streaming prose, usually only a line or two at the bottom changes per frame, so each repaint writes a few dozen bytes. That's the entire secret of the smoothness. (Certain events — the terminal getting resized, content shrinking — force an honest full redraw; Module 9 walks the real doRender with all its edge cases.)

Note · why this layer exists at all

You might wonder why pi doesn't use an existing terminal-UI library. Partly craft, partly control: streaming Markdown that reflows as it grows, inline images, custom keyboard protocols, and remote-friendly repaint sizes are all easier when you own the renderer. It's the same make-vs-buy judgment you saw with dependencies in lesson 1.5 — pi consistently chooses "make."

What you now know

Components render to arrays of strings; agent events mutate components; a throttled differential renderer repaints only the lines that changed. Your answer is on screen. One stop left in the trace: the file on disk that means this conversation isn't lost when you close the terminal.
