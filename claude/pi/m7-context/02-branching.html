Branching and forking

Conversations with agents go wrong in a specific way: five turns in, you realize turn two sent things sideways. Deleting history is lossy; starting over is wasteful. pi's answer — conversations are trees, and you can stand on any node — falls out of one field you've already met.

The tree, drawn

Mechanically it's all appends (lesson 2.7's promise, kept): every entry carries id and parentId; "the conversation" is the path from root to the leaf pointer; rewinding means appending your next message with an older entry as its parent and moving the leaf. The abandoned branch stays in the file, revisitable forever.

The user experience it buys

  • /tree — a navigator showing the whole structure; pick any node and continue from there.
  • /fork — branch from the current point into a parallel line of attack.
  • Retry a message — edit your last prompt and resend: a sibling branch, with the failed attempt preserved for comparison.
  • /resume — reopen any session at its leaf, days later.

If this feels like git — commits with parents, branches, HEAD — that's not analogy, it's the same data structure: a persistent tree grown by appending, with a movable pointer defining "current." One mental model, two tools you now understand.

The context problem branching creates

One subtlety keeps this honest. When you rewind past an assistant exchange, the model loses whatever it learned there — the abandoned branch isn't in the new path's context. Sometimes that's the point (the branch was poison); sometimes the branch did useful reconnaissance you'd hate to lose. pi's answer is branch summarization: on navigating away, it can ask a model to compress the abandoned branch into a branch_summary entry attached to the new path — "in a previous attempt, we tried X and learned Y." The knowledge survives at a fraction of the tokens. Notice the shape: summarize what you can't afford to keep verbatim. Hold that thought for one lesson — it's about to become the whole show.

Note · why trees beat undo

A linear undo stack destroys the redo branch the moment you type something new — everyone has lost work to that. Trees never sacrifice anything: every path taken remains reachable. The cost is conceptual (users must grasp "where am I in the tree?") and pi spends real UI effort (/tree's visualization, labels, summaries) paying it down. Data structures are UX decisions wearing a trench coat.

What you now know

Branching = parentId + a leaf pointer + append-only discipline: git for conversations, with model-written summaries stitching knowledge across branches. Next, the pressure that makes summarization mandatory rather than optional: the context window fills, and something must give. Compaction.
