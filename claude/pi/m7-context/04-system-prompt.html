Three consequences of the assembly design:

  • The prompt tracks the tools. Only active tools contribute their snippets — and when active tools change mid-session, AgentSession._rebuildSystemPrompt() regenerates the whole prompt. The model is never told about a tool it can't call.
  • Every layer of user gets a knob. Flags and .pi/SYSTEM.md replace the prompt entirely (for the brave); append variants add to it (for everyone else); project context arrives via files in the repo. Configuration surface mirrors confidence level.
  • Order is cache strategy. Recall exact-prefix caching (4.6): the volatile parts — date, cwd — go last, so the stable bulk of the prompt stays byte-identical across sessions and cacheable across turns. Even prose placement is economics.

LLM · System prompts: programming in prose

The system prompt occupies a privileged slot in every provider's API — models are specifically trained to weight it above user messages ("system" outranks "user" in the instruction hierarchy). It's the right home for anything that should hold for the whole session: identity, rules, environment facts, available capability.

Treat prompt text with code discipline, because it is code with a probabilistic interpreter: version it (pi's lives in git like everything else), test behavior changes when you edit it, keep it modular (note how pi composes sections rather than maintaining one sacred blob), and spend tokens like money — every word is billed on every turn, cached or not. The mystique around "prompt engineering" dissolves once you see it managed this way: it's just another config layer, with unusually fuzzy semantics.
