The plot twist: pi bypasses its own harness

Here's the fact this module has been building toward: the pi coding agent — flagship product of this repository — does not use AgentHarness. It wires its own AgentSession directly onto the low-level Agent, re-implementing persistence and compaction its own way. This is not an accident, and understanding why teaches you something textbooks won't.

The evidence

Check the coding agent's imports (the technique from lesson 1.4 — architecture claims are verified at the import line). Its central AgentSession pulls Agent, the loop types, and the message types from pi-agent-core — but no AgentHarness. It has its own SessionManager (1,600 lines, Module 7), its own compaction module with its own budgets, its own extension system (3,700 lines, Module 8). The harness's session tree and the session file format you saw in lesson 2.7 are parallel implementations of the same design — same entry types, same id/parentId tree, same leaf pointer — maintained separately.

Why would they do that?

Not ignorance — the same two people wrote both layers, in the same repo, at the same time. The realistic reasons, each a general lesson:

  • Products need custom everything, eventually. The coding agent's session entries carry coding-specific baggage (bash executions with exit codes, TUI render hints); its compaction coordinates with a UI, settings, and extension hooks; its trust model gates what loads per project. A generic harness serves the 80% case; a flagship product lives in the other 20%. When the framework's assumptions and the product's needs diverge weekly, the framework becomes friction.
  • The two layers have different customers. AgentHarness is for other people — SDK users who want an agent without building session logic (pi-chat, the Slack sibling project, is the intended audience). The coding agent is for its authors, who are happy to hand-wire because they own every piece. Library code optimizes for generality; product code optimizes for control.
  • History moves in one direction. The coding agent's infrastructure came first; the harness was extracted from its patterns as a reusable offering. Migrating the working product onto the extraction would be risk with little payoff. Codebases are archaeological sites — layers reflect when things were built, not just how they should be.

Engineering · The framework/library tension

A library is code you call; control stays with you. A framework calls your code; control inverts. Frameworks are wonderful right up until your needs leave their happy path — then every feature becomes a negotiation with someone else's assumptions. Seasoned teams therefore often ship both: a low-level library ("bring your own everything" — Agent) and a framework on top (AgentHarness), and let each consumer pick their layer. pi's own product picking the low layer isn't hypocrisy; it's the layering working as intended.

The reading skill this buys you: when you open any big codebase and find two implementations of the same idea, don't assume incompetence. Ask who consumes each, and which came first. The answer usually reveals the project's real structure better than any architecture diagram.

What it costs

Honesty requires the debit column: two session-tree implementations must now evolve in parallel (the format doc lists version migrations both must honor); improvements land twice or drift; newcomers — like you, three lessons ago — get confused about which layer is "real." The maintainers accepted those costs deliberately. Duplication is not free; it's sometimes cheaper than coupling. That sentence is worth the whole module.
