AgentTool and the LLM boundary

Welcome to pi-agent-core — 8,000 lines that turn "an API for models" into "a thing with agency." Before reading the loop itself, meet the two ideas the whole package is built on: tools that execute, and a message universe slightly bigger than what models are allowed to see.

Tool, meet execute()

In Module 3, a Tool was a name, description, and schema — pure description. The agent layer extends it into something that can act:

Every field is a decision worth reading:

  • extends Tool — an AgentTool is a Tool (structurally, lesson 3.1), so it can be passed straight into a Context; the model sees only the description half.
  • execute is typed by the schema. Static<TParameters> — the TypeBox trick from lesson 3.2, now completing its third job: the implementation receives exactly what the schema promises, or the code doesn't compile.
  • signal — cancellation reaches into tool execution (a long bash command dies when you hit Esc; lesson 5.3).
  • onUpdate — long-running tools stream partial results (bash output scrolling live in the UI comes from exactly this callback).
  • Two audiences in the result. content goes to the model (text/images only — the LLM vocabulary); details goes to humans and UIs (a structured diff, an exit code) without burning context tokens. This one split shows up in every good tool design.
  • "Throw on failure." Inside the boundary, exceptions are fine — the loop catches them and converts to isError: true results (you'll see the catch next lessons). Throw inside, return at the edges, exactly as lesson 3.6 preached.

A bigger message universe

Real applications need messages that models should never see. The coding agent records shell commands you ran, extension chatter, compaction summaries. The agent layer makes room with a one-line type and a clever hook:

TypeScript · Declaration merging

TypeScript allows an interface to be declared twice — and merges the declarations. declare module "..." lets a downstream package reopen an upstream interface and add members, at compile time only. Here the library ships CustomAgentMessages empty; the coding agent reopens it to register BashExecutionMessage, CustomMessage, and friends (the very types you saw in the session-format doc, lesson 2.7); and suddenly AgentMessage — via the indexed lookup CustomAgentMessages[keyof CustomAgentMessages], "the union of all registered value types" — includes them everywhere, fully type-checked.

Python has no real equivalent — monkey-patching changes runtime objects, while this changes only the type-level world. It's the library-extensibility idiom: the framework defines an empty registry interface, applications populate it. You'll meet it again in the TUI's keybindings and the extension events.

The boundary: convertToLlm

A bigger universe needs a customs checkpoint. The loop works in AgentMessage[] throughout — the file's opening comment says exactly that — and converts down to LLM Message[] in precisely one place: config.convertToLlm, called inside streamAssistantResponse (lesson 2.4).

The default implementation passes standard messages through and filters custom ones out. The coding agent supplies its own, which also serves as a defense layer — it strips images when the model can't see them, for instance. One function, swappable, at the narrowest point: this is how you keep an extensible system honest.

What you now know

The agent layer adds exactly two things to the pi-ai vocabulary: tools that execute (with cancellation, streaming updates, and a model/human split in their results) and an app-extensible message union with a single conversion point down to LLM reality. Now — finally — the loop, line by line.
