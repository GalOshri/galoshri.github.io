Module 1 · Orientation

What is pi?

pi is a program you run in a terminal. You type a request in plain English — "fix the failing test", "explain this function" — and a large language model reads your code, edits your files, and runs commands until the job is done. This course takes that magic trick apart, piece by piece, until you could build one yourself.

The trick, in one paragraph

A language model on its own can only do one thing: given text, produce more text. It cannot open files, run programs, or see your project. An agent is the small amount of ordinary software wrapped around a model that fixes this: it sends the model your request, and when the model answers "I'd like to read package.json" instead of answering in prose, the wrapper actually reads the file and sends the contents back. The model looks at the result, asks for the next thing — edit this file, run that test — and the wrapper obliges, around and around, until the model finally answers in prose. That wrapper-plus-loop is the whole idea. Everything else is engineering.

LLM · What "an agent" means

The word gets used loosely, but in this codebase (and this course) it means something precise: a loop that alternates between a language model and a set of tools. The model proposes tool calls; the program executes them and feeds results back; the loop ends when the model stops asking for tools. There is no hidden intelligence in the wrapper — it's a while loop you could sketch in twenty lines of Python. The model supplies the judgment; the loop supplies hands.

And here is that loop, for real

This isn't a metaphor. Deep inside pi's source there is a function called runLoop, and its core reads almost exactly like the diagram. Don't worry about the syntax yet — by Module 5 you'll read this fluently. Just notice the shape: stream a response from the model, collect its tool calls, execute them, push the results back into the conversation, repeat.

Ask the model something; if it responds with tool calls, run them and loop again; if it responds with plain text, the loop ends and you see the answer. Twenty lines of honest code. The rest of this codebase — all ~110,000 lines of it — exists to make those twenty lines work well: to talk to any model provider, to edit files safely, to draw a fast terminal UI, to remember conversations, to let users extend it.

What pi is, concretely

pi (the project calls itself the Pi agent harness) is an open-source coding agent built by Mario Zechner and Vegard Stikbakke, published as npm packages under @earendil-works. Three things make it an unusually good codebase to learn from:

  • It's real. This is not a toy tutorial repo. It ships to actual users, supports over a thousand models across ~35 providers, and handles the ugly parts — flaky networks, models that emit broken JSON, terminals with incompatible keyboard protocols.
  • It's small enough to actually finish. The core ideas live in a few thousand lines. Compare that with agents embedded in million-line products; here you can genuinely reach the bottom.
  • It's cleanly layered. The code that draws the terminal knows nothing about AI. The code that calls models knows nothing about agents. The agent loop knows nothing about coding. Each layer is a separate package you can study in isolation — and that's exactly how this course is organized.

A tour of the monorepo

pi's source is one Git repository containing five separately published packages. Before reading any code, it pays to know where everything lives and how the pieces are stitched together — because that stitching is itself a big-codebase skill.

One repo, five packages

Open the repository root and you see a thin shell — configuration, scripts, docs — around a single important directory: packages/.

This arrangement is called a monorepo: multiple packages, versioned and developed together in one repository, but published to the npm registry as five independent installable units. Someone who only wants the LLM API can npm install @earendil-works/pi-ai and never touch the rest.

Node.js · package.json and npm workspaces

Every Node package has a package.json — the equivalent of Python's pyproject.toml. It declares the package's name, version, dependencies, and runnable scripts (npm run build ≈ a Makefile target).

A workspace root is a package.json with a "workspaces" list. Running npm install there installs dependencies for all listed packages at once and — crucially — symlinks the sibling packages into each other. When coding-agent imports @earendil-works/pi-ai, npm resolves it to the local packages/ai folder, not the registry. Edit the library, and the app sees it immediately. Python's closest analogue is pip install -e for several local packages, or uv workspaces.

Two details in that file are worth savoring. First, "private": true — the root itself is never published; it exists only to coordinate. Second, look at the build script: no clever build orchestrator, just cd into each package in a fixed order and build it.   • Name and version. The @earendil-works/ prefix is an npm scope — a namespace, like a GitHub org. Notice the version: 0.80.3.   • Only three external dependencies. For a package this central, that is strikingly few. pi builds most things itself — which is precisely why it's such a good codebase to learn from.

How to read TypeScript (coming from Python)

You don't need to write TypeScript to understand this codebase — you need to read it comfortably. This lesson walks through one small, real file from pi, line by line, and builds your translation dictionary from Python as we go.

The specimen

Our file is packages/ai/src/utils/json-parse.ts. Its job is delightfully concrete: language models sometimes emit broken JSON (a raw newline inside a string, an invalid escape like \d), and this file repairs it. Under 100 lines, no clever abstractions — perfect first read.

Part 1: the imports

Line 1 is Python's from partial_json import parse as partial_parse, written backwards: the names first, the module last. The string "partial-json" names an npm package (an external dependency); you'll also see relative imports like "./types.ts" which work like Python's from .types import ….

Line 3: const declares a variable that can't be reassigned (Python has no true equivalent — think of it as an enforced convention that most variables get). new Set([...]) is exactly Python's set(...). Note the naming convention: SCREAMING_CASE for constants, camelCase for everything else where Python uses snake_case.

Node.js · ES modules, and pi's .ts imports

JavaScript historically had several competing import systems. The modern standard — ES modules (ESM) — is the import/export syntax you see here, and pi uses it exclusively ("type": "module" in every package.json). Anything a file wants to expose, it marks with export; there's no Python-style "everything is importable" — unexported names are truly private to the file.

One pi quirk: relative imports include the file extension — import … from "./types.ts". Node can strip types and run .ts files directly nowadays, and pi leans into that; the compiler rewrites the extension to .js when building the published output.

Part 2: a typed function

The signature reads like Python with the annotations made mandatory: def is_control_character(char: str) -> bool. Parameter types go after a colon; the return type goes after the parentheses.

codePointAt(0) is Python's ord(char) — except it returns undefined if the string is empty, so the next line must check for that before comparing. TypeScript forces this check: if you compared codePoint >= 0x00 without first ruling out undefined, the compiler would refuse to build. This is the single biggest difference from Python: entire categories of NoneType-style bugs die at compile time.

And !==? JavaScript has a sloppy equality (==) that coerces types, and a strict one (===). Well-written code — including all of pi — uses the strict forms exclusively. Read ===/!== as Python's ==/!=.

TypeScript · Static types that vanish at runtime

TypeScript is JavaScript plus type annotations. The types are checked by a compiler and then erased — what actually runs is plain JavaScript with the annotations deleted. Python's type hints are the right mental model, with one huge difference in enforcement: mypy is optional and often skipped; TypeScript's checker gates the build, so pi's code simply cannot ship with a type error.

Besides annotations, TypeScript adds ways to describe shapes: interface Point { x: number; y: number } is like a dataclass declaration that exists only for the checker — no class is created, no memory allocated. Any object with those fields satisfies it. pi's core vocabulary (Message, Tool, ToolCall) is defined this way, as pure shape descriptions. You'll meet them in Module 3.

Part 3: the main loop

export marks this function as the file's public API. let declares a reassignable variable (contrast with const). The classic three-part for loop is just for index in range(len(json)); you'll also see the cleaner for (const char of json), which is Python's for char in json.

The algorithm itself is a hand-rolled state machine: walk the string character by character, tracking whether we're inside a JSON string literal, and repair problems as they pass by. Notice how readable this is — no regex golf, no dependencies. You could port it to Python in ten minutes, and that feeling of "I could write this" is exactly what you should calibrate to. Most production code is not clever.

Part 4: braces, semicolons, and other noise

The remaining differences are pure surface. Blocks use { } instead of indentation (though the code is indented anyway, so your eyes can ignore the braces). Statements end with semicolons. Comments are // and /* */ instead of #, with /** ... */ "doc comments" playing the role of docstrings — you saw one atop repairJson in the real file:

Where did the "compile" step go? What's tsgo?

The layered architecture

You've seen that pi's five packages form a straight dependency line. This lesson is about why that line is the most important design decision in the repository — and how to verify architectural claims like this one yourself, from the code, rather than taking documentation on faith.

The rule: dependencies point one way

Spelled out, the contract is:

  • pi-tui knows how to render text and read keystrokes. It contains the word "terminal" thousands of times and the word "model" zero times. You could use it to build a terminal Tetris.
  • pi-ai knows how to send messages to LLM providers and stream responses back. It has no concept of an agent, a tool executing, or a screen. You could use it to build a chatbot with no loop at all.
  • pi-agent-core knows the loop: send context, collect tool calls, execute, repeat. It doesn't know the tools are about coding — it would run a cooking agent just as happily. And it has no user interface whatsoever.
  • pi-coding-agent is where it all becomes a product: coding tools (read/edit/bash), a terminal chat UI, session files, settings. It writes almost no fundamentals itself — it composes the three layers below.

Don't trust the diagram — check the imports

In a big codebase, architecture documents drift out of date. The ground truth is always the import statements. Here are the first lines of the agent loop's source file — the heart of pi-agent-core:

Two imports: the package one layer down (pi-ai), and its own local types. No pi-tui, no pi-coding-agent — the loop literally cannot mention a screen or a coding tool, because nothing of the sort is in scope. Meanwhile pi-tui's own manifest lists exactly two external dependencies — a Markdown parser and a Unicode-width table — and zero internal ones. The architecture isn't a promise; it's mechanically enforced by what each package is allowed to import.

Engineering · Dependency direction and layering

The deepest idea in large-scale code organization: stable things should not depend on volatile things. "What a message is" changes rarely; "how the footer looks" changes weekly. By forcing all arrows to point from volatile (product) to stable (primitives), a change at the top can never break the bottom, and each lower layer can be understood, tested, and reused in isolation.

The classic smell to watch for is the cycle: A imports B and B imports A, which means neither can be understood alone and they're really one tangled unit. Python projects fight the same battle with circular import errors — the difference here is that the package boundary makes the layering physical. packages/tui could not import the agent even by accident; npm wouldn't resolve it.

What the layering buys, concretely

Three real payoffs you'll witness during this course:

  • Reuse. The same pi-agent-core that powers this terminal app also powers pi-chat, the team's separate Slack-automation project. No UI in the loop means any UI can be bolted on — including "no UI at all," which is exactly what pi's headless RPC mode is (Module 10).
  • Testability. Because pi-ai hides all providers behind one interface, the test suite swaps in a scripted fake provider (the "faux" provider, Module 4) and tests the entire agent stack without network calls or API bills.
  • Learnability. This one benefits you directly. Each module of this course studies one layer while treating the layer below as a solved black box. That's not a teaching simplification — it's genuinely how the code is built, and how professionals navigate any large system: pick a layer, trust its neighbors' contracts.

Where the seams show

Real codebases are never perfectly clean, and honest reading means noticing the seams. Two you'll meet later: pi-agent-core ships a "batteries included" harness layer that the coding agent ignores, preferring to hand-wire its own (the plot twist of Module 5); and the coding agent's interactive mode is a single 5,800-line file that composition didn't save from growing huge (Module 6 turns reading such files into a skill). Layering constrains where mess can live; it doesn't abolish mess.

What you now know

pi is four one-way layers plus an experiment on top. When you're lost at any point in this course, come back to one question: which layer am I in, and what does it import? How the project keeps itself honest

Big codebases don't stay coherent because everyone is careful. They stay coherent because machines refuse incoherent code. This lesson tours pi's enforcement machinery — and its most unusual artifact: a rulebook written for AI contributors.

The gate: npm run check

One command must pass before any commit lands. Here it is from the root manifest, and it's worth reading slowly because it's a whole philosophy in one line:

Left to right (each && means "and only if that succeeded"):

  • biome — a combined formatter and linter (one fast tool replacing the traditional ESLint + Prettier pair; think ruff format + ruff check fused together). --write autofixes what it can; --error-on-warnings means warnings are failures. There is no "we'll clean it up later" tier.
  • check:pinned-deps — a custom script asserting every external dependency is pinned to an exact version. More below.
  • check:ts-imports — enforces the house style that relative imports spell out the .ts extension.
  • tsgo --noEmit — the TypeScript compiler in check-only mode: type-check all ~110k lines, emit nothing. The mypy --strict of the operation, except non-negotiable.

A husky pre-commit hook (a small tool that installs Git hooks from the repo) runs this entire pipeline automatically before every commit. You physically cannot commit unformatted or type-broken code from a normal setup.

Paranoia as policy: dependencies

The most distinctive part of pi's tooling has nothing to do with types. The project treats every third-party package as a potential attack. From the rulebook:

Engineering · Supply-chain attacks and lockfiles

When you install a dependency, you're running someone else's code on your machine — and npm packages can register lifecycle scripts that execute arbitrary commands at install time. Compromise one popular package (or one maintainer's laptop) and you compromise everyone who installs it. This is a supply-chain attack, and npm has suffered several famous ones; Python's PyPI has too.

pi's defenses, in order: exact version pins (a range like ^7.0.0 would silently adopt whatever 7.0.1 turns out to be; 7.0.5 adopts nothing), a lockfile recording the hash of every package in the whole tree (like uv.lock), --ignore-scripts on every install so lifecycle scripts never run, and an allowlist for the rare dependency that genuinely needs one. Notice these are process defenses, enforced by scripts and hooks — not vigilance.

Tests

About 294 test files sit in per-package test/ directories — the coding agent alone has 161. The repo's honest wrinkle: two test runners. Three packages use vitest (a pytest-like runner); pi-tui uses Node's built-in node --test. Real projects accrete history like this. Two details worth stealing:

  • Tests that would hit paid LLM APIs activate only when auth environment variables are present; the default ./test.sh run costs nothing and touches no network. Agent tests run against the scripted faux provider instead (Module 4).
  • The TUI test directory is full of files with names like bug-regression-…-cjk-width.test.ts: each past bug froze into a permanent test. That's what "the codebase remembers" looks like.

You press Enter

For the next seven lessons we follow one message through the whole machine. You've started pi in some project and typed: "what does package.json do?" — and now you press Enter. This lesson covers the journey's first inch: from keystroke to a call on the agent.

How to read this module

We fly at 500 feet. Every stop on the route gets a sentence of "how" and a pointer to the module that gives it the full treatment. If a detail nags at you — good; a later module almost certainly scratches that itch.

Setting: a terminal in raw mode

A terminal normally handles typing for you: it echoes characters, lets you backspace, and delivers input to the program only when you press Enter (so-called "cooked" mode). A rich interface like pi's can't live with that — it needs every keystroke as it happens, to update the display, offer autocompletions, and react to shortcuts. So on startup pi switches the terminal to raw mode: echo off, buffering off, every key delivered immediately as bytes. From that moment, everything you see on screen — including the characters you "type" — is drawn by pi itself. (Module 9 covers this machinery in loving detail.)

Your keystrokes flow into an Editor component — a from-scratch text editor (2,300 lines! with undo, kill-ring, autocomplete) that pi renders at the bottom of the screen. As far as this module is concerned it's a text box. What matters is what happens when Enter arrives.

Node.js · async/await, and where the parallelism isn't

Every interesting line here says await: the code pauses at that point until a slow operation (a network response, a file read) completes, without freezing the program — other work, like repainting the screen, proceeds meanwhile. If you know Python's asyncio, this is the same async def/await idea with one glorious simplification: there is no event-loop bookkeeping. No asyncio.run(), no "am I in a loop?" errors. One thing async does not give you is parallel CPU work — JavaScript is single-threaded, like Python-with-GIL but stricter. You lose the ability to "edit history" and gain crash-safety, a full audit trail, and trivially correct concurrent readers. Databases build their write-ahead logs this way; Git's object store, Kafka, and accounting ledgers are all the same idea. The interesting part: parameters

This is also your first proper look at generics. The extends clause means "T must at least be a schema" — Python's TypeVar("T", bound=TSchema). You'll see this pattern constantly: a container type, one type parameter, a constraint.

EventStream: an async iterable by hand

Between the adapter that produces events and the loop that for awaits them sits an 89-line class. It's the best small file in the repository for understanding how async JavaScript actually works — because it builds the machinery you normally take for granted.

The problem it solves

A producer (the network adapter) pushes events whenever they arrive. A consumer (the agent loop) pulls events whenever it's ready. Sometimes the producer is ahead (events must queue); sometimes the consumer is ahead (it must sleep until something arrives). And one consumer just wants the final answer, not the play-by-play. EventStream handles all three with a queue, a list of waiters, and a promise.

The whole class, in three walkthroughs

Generic over two types: T, the events, and R, the final result (for assistant streams: events in, AssistantMessage out). The state is honest bookkeeping — queue holds events nobody has consumed; waiting holds, in effect, paused consumers. The constructor trick deserves a pause: it creates a Promise and smuggles out its resolve function into a field, so the class can settle the promise later, from anywhere. (The ! tells the compiler "trust me, this gets assigned" — the executor runs synchronously, so it does.)

push is synchronous and cheap. If this event is terminal (a done/error, per the isComplete predicate), settle the final-result promise. Then the handoff: if a consumer is parked in waiting, hand the event straight to it — calling a stored resolve function is how you wake a sleeping async function. Otherwise, queue it.

Three states per lap: events queued → yield one; stream finished → stop; otherwise → park: create a promise, push its resolve function onto waiting, and await. The consumer is now suspended at zero cost until push calls that resolve. This producer/consumer handshake through stored resolvers is the fundamental move of async programming — queues, channels, and semaphores are all elaborations of it.

Node.js · Promises under the hood

A Promise is just a box that will hold a value later, plus a list of callbacks to run when it does. new Promise((resolve) => ...) gives you the trigger: whoever holds resolve holds the power to complete the box. await p means "suspend me; add my continuation to p's callback list." That's all — no threads, no magic. Python's asyncio.Future with set_result() is the same object with a different accent.

Two idioms from this file worth keeping: the stored resolver (make a promise, keep its resolve for later — how you bridge callback-world and await-world), and the shared settled promise — result() returns the same promise to every caller, and a promise that's already settled delivers its value immediately to late arrivals. That's why the agent loop can call response.result() after consuming the whole stream and still get the final message (you saw it do exactly that in lesson 2.4).

The specialization

The generic machinery, bound to last lesson's grammar: complete on done or error, extract the final AssistantMessage either way. Every provider adapter returns one of these; the agent layer builds its own EventStream<AgentEvent, AgentMessage[]> from the same class. One 89-line utility, two layers served.

Why hand-roll this instead of using an async generator?

An async function* is pull-driven: its body only advances when a consumer asks for the next value. But a network socket pushes data on its own schedule, whether or not anyone is pulling, and pi also needs the side-channel result() promise and multi-phase completion semantics. A hand-rolled push-queue gives producer and consumer each their own tempo, with the class as shock absorber. (Python folks: this is asyncio.Queue grown a result future.)

An async iterable is not magic: it's a queue, a list of parked resolvers, and the discipline to wake exactly one sleeper per event. You now understand every mechanism behind for await (const event of response). One lesson left in this module: the wrapper that guarantees these streams never throw.

lazy.ts: errors become events

Seventy lines that encode pi-ai's sternest design rule: once you ask for a stream, nothing throws — ever. Auth failure, missing module, dead network: all of it arrives as a normal error event. This lesson shows how, and why the rule is worth the ceremony.

The contract, stated in the types

Why insist? Think about the consumer. The agent loop handles a model response with one code path: iterate events, check stopReason. If setup failures threw exceptions instead, every caller would need try/catch around the loop plus the event handling inside it — two error channels, forever, in every consumer, in every UI, in every extension. Funneling all failure through the event grammar means one channel. You've already reaped the benefit twice without noticing: the loop's simple stopReason === "error" check in lesson 2.3 handles network catastrophes and polite refusals identically.

The problem: failure before the stream exists

There's a wrinkle. A stream function must return a stream synchronously, but its setup work — resolving OAuth tokens, dynamically importing the adapter module — is async and can fail before any stream exists to emit an error on. The fix is delightfully simple: return an empty stream immediately, do setup behind it, and pipe either the real events or a synthesized error into it.

Last lesson's EventStream, earning its keep: because a push-queue can exist before its producer does, the caller gets a real, iterable stream on the very same tick, while setup() races ahead in the background. Success → forward the inner stream's events into the outer one. Failure → .catch converts the exception into a synthetic AssistantMessage (empty content, stopReason: "error", zeroed usage — a perfectly ordinary message that happens to describe a disaster) and pushes it as the terminal event. The exception dies here; data crosses the boundary.

The second export wraps a whole adapter module. That load argument is a dynamic import() — the Anthropic provider you read in lesson 3.3 doesn't actually pull in the 1,200-line adapter until the first request needs it. Fast startup, and a failed module load becomes… you guessed it, an error event.

Engineering · Errors as values at API boundaries

Exceptions are goto with better manners: they teleport control to wherever the nearest catch happens to be, invisibly to type signatures. Within a small scope that's fine. But across an API boundary — where the caller might be a loop, a UI, a queue consumer — exceptions force every caller to know the throw behavior of everything beneath them, and async makes it worse (a rejection escaping a background task can kill the process).

The alternative: make failure part of the return type. Rust's Result, Go's err, and pi's stopReason: "error" messages are one family. The cost is honesty-by-boilerplate — you must check. The payoff is that the type system won't let you forget failure exists, and callers get one channel to handle. Rule of thumb worth stealing: throw inside, return at the edges.

Watch the layers compose

Errors get this treatment at every altitude, in the same costume:

  • Setup fails → lazyStream emits an error event (this lesson).
  • Provider fails mid-stream → the adapter catches it and emits an error event (next module).
  • The loop sees stopReason: "error" → ends the run gracefully, message preserved (lesson 2.3).
  • A tool fails → a ToolResultMessage with isError: true, and the model reads the failure (lesson 2.5).
  • The session file records the error message like any other — crashes are data, auditable next morning (lesson 2.7).

One philosophy, five layers, zero try/catch in any consumer. When an architecture repeats a choice this consistently, that choice is doing structural work.

Repairing broken JSON

You met json-parse.ts in lesson 1.3 as a syntax specimen. Now you know enough to appreciate what it's for: language models produce structured output the way toddlers produce sentences — usually right, never guaranteed. pi plans for that.

The three ways model JSON goes wrong

Tool-call arguments are JSON written by a text generator, and they fail in three characteristic ways:

  • Truncation. During streaming, arguments arrive in fragments — '{"pa' is the steady state, not an anomaly (lesson 3.4's event trace). And when a response hits its token limit (stopReason: "length"), even the final JSON can be cut off mid-string.
  • Raw control characters. A model writing a file via a tool happily puts real newlines inside a JSON string — where the spec demands \n. Strict parsers reject the whole call.
  • Invalid escapes. Regex-heavy arguments produce "\d+" — and \d is not a legal JSON escape. One backslash, entire tool call rejected.

LLM · Why model output is unreliable structured data

A model emits tokens by sampling a probability distribution — nothing mechanically constrains token 47 to close the brace opened by token 12. Providers improve the odds (fine-tuning on tool calls; some offer constrained decoding — that's the strict flag from the compat lesson), but the client can't count on it, and with twenty vendors of varying quality, "usually valid" is the ceiling.

So robust agents treat model output like user input: parse defensively, repair when possible, validate against a schema, and let failures flow back as data. pi does all four — repair here, schema validation in the loop (lesson 2.5), and a isError: true tool result if it's still hopeless, so the model gets to try again. Nothing crashes because the model typo'd.

Prompt caching and the cost ledger

An agent's dirty secret: it re-sends an ever-growing transcript on every single turn. Without countermeasures, a long session's bill grows quadratically. This lesson covers the countermeasure — prompt caching — and the bookkeeping that lets pi print an honest price at the bottom of your screen.

The quadratic problem

Statelessness (lesson 2.2) has a price. Turn 1 sends the system prompt + your message: say 5,000 tokens. Turn 2 resends all of that plus the tool result: 15,000. Turn 10 might send 80,000 — and you pay input rates on all of them, every turn. Sum over a session and the transcript you re-uploaded dominates everything else you ever paid for.

LLM · Prompt caching economics

Providers noticed that consecutive requests usually share a huge prefix — same system prompt, same tools, same early conversation. So they offer a deal: mark the shared prefix, and the provider keeps its processed form (the model's internal key/value state) warm for a few minutes. On the next request, re-reading the cached prefix costs ~10% of the normal input rate — Claude Sonnet: $3.00/M fresh vs $0.30/M cached. Writing the cache costs a ~25% premium ($3.75/M), and Anthropic's 1-hour retention tier costs 2× base input.

The catch: caches match by exact prefix. Change one early byte — reorder a tool, tweak the system prompt mid-session — and everything after that byte re-runs at full price. That's why agent harnesses are fanatical about keeping context append-only: pi's conversation only ever grows at the end, precisely so the prefix stays byte-stable. A data-structure decision (lesson 2.7's append-only instinct) turns out to be a pricing strategy.

Three engineering points worth keeping, even at flyover altitude:

  • Tokens expire; design for mid-session refresh. Access tokens last minutes-to-hours. Now the odd detail from lesson 2.4 pays off: the agent loop resolves the API key fresh on every model call precisely because "the key" may need to be a just-refreshed token.

runLoop, part 1: a turn

The centerpiece of the course. You've seen runLoop condensed (lesson 1.1) and flowcharted (lesson 2.3); now you have every concept needed to read the real thing — and this time we keep all the details: steering, error paths, turn events, and the hooks that let an application reshape a run in flight.

The full skeleton, honestly

Look at the parameters: everything arrives injected. Context (the conversation + tools), config (a bag of functions — the hooks), an abort signal, an event sink, a stream function. runLoop owns no state of its own; it's a pure orchestrator. Note also the very first line of logic: check for steering messages before doing anything, because the user may have typed while a previous operation was settling. (The ?.() is optional chaining — "call it if it exists" — since every hook is optional.)

Injected messages get the full event ceremony (message_start/message_end) — so the UI displays your steering text and the session file records it, through the same broadcast machinery as everything else. Consistency like this is why subscribers (lesson 2.2) can be simple.

The whole error story of Modules 3–4, condensed to two lines of consumer code: failures arrive as ordinary messages with a stopReason, get announced like any turn, and end the run cleanly. No try/catch. The failed message is already in the context and the session file — tomorrow you can resume the conversation and the model will see what went wrong.

The heartbeat you already know — filter for tool calls, execute, append results — plus one subtlety: terminate. A tool batch can vote to stop the loop even though tools ran (a plan-approval tool, say, whose whole point is "pause here for the human"). hasMoreToolCalls = !executedToolBatch.terminate is that vote being counted.

The seams: hooks between turns

What happens after turn_end is the loop's quiet superpower:

Four hooks, four capabilities, all owned by the caller: prepareNextTurn may swap the model, the thinking level, or even the whole context between turns — this is where the coding agent triggers compaction when the conversation nears the context window (Module 7). shouldStopAfterTurn is a policy veto (cap turns, stop on budget). getSteeringMessages is polled after every turn — your mid-task "actually, use spaces not tabs" enters here, before the next model call. getFollowUpMessages is polled only when the agent would otherwise finish — queued follow-up work starts a fresh inner loop without ending the run.

Count what runLoop does not know: no retry policy, no compaction strategy, no turn limits, no UI, no persistence. Every opinion is a config function with a ?. — absent by default, supplied by whoever has the context to decide. This is the "mechanism, not policy" principle (old Unix wisdom), and it's why this one loop can power a terminal product, a Slack bot, and a test harness unchanged. When you build your own agent — and after this module you genuinely could — resist putting policy in the loop. The loop should be boring; boring cores age well.

Module 5 · pi-agent-core: The Loop

runLoop, part 2: executing tools

When the model asks for three file reads at once, must they run one by one? Executing tool calls is a small pipeline with real decisions: parallelism, validation, permission hooks, cancellation, and error envelopes. It's also where extensions will later plug in their power.

Choosing a strategy

Default: parallel — three reads overlap their waiting and finish together (remember, JavaScript concurrency is overlapping I/O waits, lesson 2.3). But one tool marked executionMode: "sequential" forces the whole batch sequential: if an edit is in the mix, you don't want a bash racing it. Conservative, simple, correct-by-default.

Each call: a three-stage pipeline

Four gates before any tool code runs. Does the tool exist? (Models hallucinate tool names; that's an error result, so the model reads it and corrects itself.) Can the args be fixed? (prepareArguments absorbs model quirks — some models send the edits array as a JSON string.) Do they satisfy the schema? (lesson 3.2's third job.) Does anyone object? — beforeToolCall can block the call with a reason. That one hook is the foundation of every permission system in Module 8: "ask the human before bash runs" is an extension returning { block: true }. Note the return shape: "immediate" vs "prepared" — another discriminated union, steering the pipeline.

The actual execution, wearing three seatbelts: the onUpdate callback forwards partial results as events (live bash output!) but flips acceptingUpdates off when the tool settles — a straggling callback from a sloppy tool can't emit ghost events; all update events are awaited before returning — no event ever arrives after its tool's end event; and the catch converts any throw into an error result. Remember the AgentTool contract said "throw on failure"? Here's the net that makes that safe.

The exit interview: afterToolCall may rewrite anything — truncate a huge output, redact a secret, flip a result to an error, or set terminate. The ?? operator ("use the left side unless it's null/undefined") makes the rewrite surgical: override only what you return. Then the result is wrapped as the ToolResultMessage you know from lesson 2.5 and announced on the broadcast.

Parallel, but orderly

The parallel variant has one elegant subtlety: it prepares calls one by one (validation and blocking hooks stay deterministic), collects the executions as an array of pending functions, runs them concurrently via Promise.all — and then emits the result messages in the assistant's original call order, regardless of which finished first. Models expect results to line up with their requests; the wall-clock race stays invisible.

Node.js · AbortController and AbortSignal

Cancellation in JavaScript is cooperative and flows through two tiny classes: an AbortController has a .signal and an .abort() method; you hand the signal to everything you might want to stop. fetch aborts the HTTP request natively; your own code checks signal?.aborted at sensible points — as this pipeline does between stages, and as the SSE reader did in lesson 4.2.

Trace the whole journey: you press Esc → the Agent's AbortController.abort() fires → the same signal object, threaded through loop → stream → adapter → tools, flips everywhere at once → the model request dies mid-flight, running tools wind down, and the run ends with stopReason: "aborted" — as data, in the session file. Python's closest analogue is asyncio task cancellation, but signals are more explicit: you can see in every function signature whether it's cancellable, because the signal parameter is right there.

What you now know

Tool execution = strategy choice, then prepare/execute/finalize per call, with validation and two rewrite hooks, ghost-proof streaming updates, order-preserving parallelism, and a cancellation signal threaded through everything. Engineering · Backpressure, or: why await your listeners

The cheap way to broadcast is fire-and-forget: call listeners, don't wait. Fast — and it lets a slow consumer fall arbitrarily far behind the producer while events pile up in memory. pi chooses the opposite: the loop itself does not advance until every subscriber has finished with the event. The session file has the message before the next model call starts; the UI is never rendering a stale world; an extension's veto genuinely happened before the next step.

This is backpressure — consumers throttling producers — the same idea as bounded queues in classic producer/consumer designs. The price is honest: one slow listener slows the whole agent. pi pays it because an agent's event rate is modest and correctness of the record (that JSONL file is a crash-safe audit log only if writes settle in order) beats raw throughput. Know which side of that trade your system needs.

Queues with a personality

steer() and followUp() feed two of these; the loop's getSteeringMessages/getFollowUpMessages hooks drain them. The mode matters more than it looks: default is "one-at-a-time", so if you fired off three steering thoughts while the model worked, they arrive one per turn — each getting its own model response — rather than as a confusing pile. A four-line method encoding a UX decision.

Run lifecycle: the safety wrapper

The last line of defense: if something does throw past all the nets below (a bug, not a provider failure), the Agent synthesizes a proper error AssistantMessage and plays the full event ceremony for it — so the UI shows it, the session records it, and every subscriber sees a well-formed ending. Even bugs die as data. Note also the one-run-at-a-time guard and the guarantee behind isStreaming: it stays true until agent_end listeners settle — "idle" means everyone is done, not just the loop.

The plot twist: pi bypasses its own harness

Here's the fact this module has been building toward: the pi coding agent — flagship product of this repository — does not use AgentHarness. It wires its own AgentSession directly onto the low-level Agent, re-implementing persistence and compaction its own way. This is not an accident, and understanding why teaches you something textbooks won't.

The evidence

Check the coding agent's imports (the technique from lesson 1.4 — architecture claims are verified at the import line). Its central AgentSession pulls Agent, the loop types, and the message types from pi-agent-core — but no AgentHarness. It has its own SessionManager (1,600 lines, Module 7), its own compaction module with its own budgets, its own extension system (3,700 lines, Module 8). The harness's session tree and the session file format you saw in lesson 2.7 are parallel implementations of the same design — same entry types, same id/parentId tree, same leaf pointer — maintained separately.

Why would they do that?

Not ignorance — the same two people wrote both layers, in the same repo, at the same time. The realistic reasons, each a general lesson:

  • Products need custom everything, eventually. The coding agent's session entries carry coding-specific baggage (bash executions with exit codes, TUI render hints); its compaction coordinates with a UI, settings, and extension hooks; its trust model gates what loads per project. A generic harness serves the 80% case; a flagship product lives in the other 20%. When the framework's assumptions and the product's needs diverge weekly, the framework becomes friction.
  • The two layers have different customers. AgentHarness is for other people — SDK users who want an agent without building session logic (pi-chat, the Slack sibling project, is the intended audience). The coding agent is for its authors, who are happy to hand-wire because they own every piece. Library code optimizes for generality; product code optimizes for control.
  • History moves in one direction. The coding agent's infrastructure came first; the harness was extracted from its patterns as a reusable offering. Migrating the working product onto the extraction would be risk with little payoff. Codebases are archaeological sites — layers reflect when things were built, not just how they should be.

Engineering · The framework/library tension

A library is code you call; control stays with you. A framework calls your code; control inverts. Frameworks are wonderful right up until your needs leave their happy path — then every feature becomes a negotiation with someone else's assumptions. Seasoned teams therefore often ship both: a low-level library ("bring your own everything" — Agent) and a framework on top (AgentHarness), and let each consumer pick their layer. pi's own product picking the low layer isn't hypocrisy; it's the layering working as intended.

The reading skill this buys you: when you open any big codebase and find two implementations of the same idea, don't assume incompetence. Ask who consumes each, and which came first. The answer usually reveals the project's real structure better than any architecture diagram.

What it costs

Honesty requires the debit column: two session-tree implementations must now evolve in parallel (the format doc lists version migrations both must honor); improvements land twice or drift; newcomers — like you, three lessons ago — get confused about which layer is "real." The maintainers accepted those costs deliberately. Duplication is not free; it's sometimes cheaper than coupling. That sentence is worth the whole module.

Tools: read, ls, grep, find

The observation tools — the model's eyes. Their schemas are trivial; their engineering is entirely about one scarce resource. A file is megabytes; the model's attention is a fixed number of tokens; every tool that produces output must therefore budget output.

LLM · The context window as a scarce resource

A model reads at most its context window — for Claude Sonnet, 200k tokens, maybe 150k words — and that budget holds everything: system prompt, conversation, every tool result ever returned this session. Worse, the budget is shared over time: a wasteful tool result doesn't just crowd this turn, it gets re-sent (and re-billed, lesson 4.6) on every future turn until compaction reaps it.

So agent tools obey an economy of attention: return the least output that answers the question, tell the model what was withheld, and give it knobs to ask for more. The bash tool

The most powerful tool in the box: arbitrary shell commands, which is to say everything. Its schema is two fields; its implementation is 470 lines of process management — and the gap between those numbers is this lesson.

Spawning like you mean it

Node.js · child_process, vs Python's subprocess

spawn(cmd, args, options) is subprocess.Popen: start a process, get back a handle with stdout/stderr streams and events. The idiomatic difference: where Python often blocks on proc.communicate(), Node code subscribes — child.stdout.on("data", ...) — and stays responsive (the event-driven style Python asyncio gets via create_subprocess_exec).

The options here are all deliberate. cwd: run where the agent works. env: a curated login-shell environment. stdio: pipe the outputs, ignore-or-pipe stdin. And the crucial one — detached: true — puts the child in its own process group, which looks pointless until you need to kill it.

The kill problem

Run npm test and the shell spawns node, which spawns workers, which spawn more workers. Kill only the shell and the grandchildren keep running — orphaned test suites chewing CPU behind your back. The fix is the process group: with detached, killing the group (killProcessTree sends the signal to -pid, the negative PID meaning "everyone in the group") takes the whole family down. Note the paranoid details: checking signal.aborted before subscribing (the abort may have happened already), { once: true }, and a finally that unhooks everything — listener leaks in long-lived processes are how memory quietly disappears. The trackDetachedChildPid registry is the last resort: if pi itself dies, an exit handler still knows which orphans to reap.

Output: streaming and two-sided truncation

Both stdout and stderr feed an OutputAccumulator — interleaved in arrival order, like a real terminal. It solves two problems at once: streaming — partial output flows through the tool's onUpdate callback (lesson 5.3), which is why you watch test output scroll live; and budgeting — but with a twist. For bash, the end of output usually matters most (the error is at the bottom of the build log), so bash truncates from the head (truncateTail keeps the tail), the opposite of read. When output is huge, the accumulator spills the full transcript to a temp file and tells the model the path — so the model can grep the full log if it needs the middle. The scarce resource gets the summary; the filesystem keeps the truth.

The shell itself

getShellConfig() (in utils/shell.ts) picks your login shell — zsh, bash, fish, PowerShell on Windows — with its rc files, so the model's commands see the same aliases, PATH and node version you see. Agents that spawn a bare /bin/sh mysteriously can't run half of what their users can; this is that bug, pre-fixed. And note what pi deliberately does not add: no sandbox, no allow-list — the README says plainly that pi runs with your permissions, and containment is your job (or an extension's: lesson 8.3 shows a permission gate, and there's a pluggable BashOperations for routing commands into VMs). The tool's honesty about its danger is itself a design decision.

edit, write, and fuzzy matching

How does a language model edit a file it can't see the bytes of? pi's answer — search-and-replace with carefully bounded forgiveness — lives in edit-diff.ts, home of the most instructive algorithm in the repository.

The edit contract

The edit tool's schema: a path plus an array of { oldText, newText } pairs. The model quotes a snippet it believes is in the file, and supplies the replacement. Three rules give the contract its safety:

  • Each oldText must be found — or the whole edit fails with a teaching error: "Could not find the exact text in … The old text must match exactly including all whitespace and newlines." (Error messages addressed to a model are prompts; this one trains it to quote more carefully.)
  • Each match must be unique — "Found 3 occurrences … Please provide more context to make it unique." Ambiguity never silently picks a winner.
  • All edits match against the original file, not the output of earlier edits in the batch — so the model can't confuse itself about intermediate states.

The problem: models misquote invisibly

The model saw the file through read, possibly turns ago, filtered through tokenization. When it quotes oldText back, tiny corruptions creep in: a trailing space dropped, an en-dash where the file has a hyphen, curly quotes for straight ones. Engineering · Unicode normalization, or "identical" strings that aren't

Unicode lets the same visible text have different byte encodings: é as one codepoint or as e + a combining accent; a dozen kinds of dash; six kinds of invisible space. "café" === "café" can be false. The standard fix is a normalization form — NFKC maps compatibility variants (fullwidth letters, ligatures, composed accents) to one canonical encoding. Python has it too: unicodedata.normalize("NFKC", s).

The design insight here isn't the API, it's the restraint: normalize only what's cosmetically invisible (quotes, dashes, trailing spaces), never anything meaningful (indentation, case, actual words) — and do the search entirely in normalized space for both haystack and needle, so offsets stay coherent. Fuzzy matching that's too fuzzy would silently edit the wrong code, which is catastrophically worse than failing. Bounded forgiveness.

Around the match, the file logic preserves what the model never sees: CRLF vs LF line endings detected and restored, a UTF-8 BOM stripped and re-attached (stripBom), and a unified diff produced for the UI — the pretty red/green block you see after every edit is computed here, not by git.

write, and the mutation queue

write is comparatively boring — create/overwrite a file with content — with one shared subtlety: both mutating tools wrap their work in withFileMutationQueue, which serializes operations per file path. Remember that tool calls run in parallel by default (lesson 5.3); two edits to the same file racing each other would corrupt it. A per-path promise queue means edits to different files still overlap while same-file operations line up. Concurrency control scoped exactly to the actual hazard — nothing global, nothing coarse.

Note · why not just regenerate the whole file?

Early agents did "write the full new version" — simple, and it burns output tokens proportional to file size (expensive, lesson 4.6), risks the model silently dropping code it forgot, and makes diffs unreviewable. Targeted search-replace edits cost tokens proportional to the change, fail loudly when the model's memory of the file is stale, and produce human-auditable diffs. Every serious coding agent converged on some version of this design.

Session persistence

You met the session file in lesson 2.7 as a reader; this module owns it as an engineer. SessionManager (1,611 lines) is the coding agent's memory organ — and its design decisions echo databases far more than chat apps.

The write path: one line, synchronously

Two choices worth pausing on. appendFileSync — the synchronous variant, in a codebase that's async everywhere else. Deliberate: an append of one JSON line is microseconds, and doing it synchronously means the entry is durably queued for disk before anything else proceeds — no interleaving hazards, no "the process died with writes in flight." Remember the awaited-listener guarantee (lesson 5.4)? The session subscriber runs this persist inside message_end, so the loop cannot start the next model call until the current message is on disk. Crash-safety by composition of two small guarantees.

And who calls it: the thread you traced in lesson 6.3 — AgentSession._handleAgentEvent, case message_end. Persistence is just another subscriber to the broadcast; the loop doesn't know disk exists.

What gets persisted: more than messages

The entry-type vocabulary matches the harness tree from lesson 5.5 almost one-for-one (this is the parallel implementation from the plot twist): message, model_change, thinking_level_change, compaction, branch_summary, custom, label, session_info. Every configuration change is a fact in the log, so replay reconstructs not just the words but the circumstances. The extended message roles (lesson 5.1's declaration merging, realized): bashExecution for commands you ran with the ! prefix, custom for extension data — each with an excludeFromContext-style say over what the model later sees.

Reading it back: buildSessionContext

On pi --resume (or /resume), the manager parses the JSONL, walks root-to-leaf, and folds the entries into a SessionContext — the same reducer pattern as the harness's version (lesson 5.5): messages accumulate, the last model_change wins, a compaction entry resets the visible-message window. Then version migrations: the header records a format version (currently 3), and old files upgrade on load — v1 linear sessions become trees, renamed roles get mapped. Your conversations from three months of pi versions ago still open. That's what a stable on-disk format costs and buys.

Where files live, and the lifecycle

Directory per working directory (slashes → dashes), file per conversation, named by timestamp + UUID. No database, no index — the filesystem is the database. Listing your sessions for /resume is a directory read; deleting a conversation is deleting a file; backup is copying a folder. For single-user local data with this write pattern, files beat SQLite on every axis that matters here: transparency (you can cat your history), robustness (no schema migrations for a DB engine), and grep-ability.

Note · the session file is an API

Because the format is documented (docs/session-format.md) and stable, other programs build on it: cost-analysis scripts in the repo's scripts/ read session files; exporters turn them into HTML; the /share command uploads them. When a file format outlives any single feature, treat it as a public API — version it, document it, migrate it. pi does all three.

Branching and forking

Conversations with agents go wrong in a specific way: five turns in, you realize turn two sent things sideways. Deleting history is lossy; starting over is wasteful. pi's answer — conversations are trees, and you can stand on any node — falls out of one field you've already met.

The tree, drawn

Mechanically it's all appends (lesson 2.7's promise, kept): every entry carries id and parentId; "the conversation" is the path from root to the leaf pointer; rewinding means appending your next message with an older entry as its parent and moving the leaf. The abandoned branch stays in the file, revisitable forever.

The user experience it buys

  • /tree — a navigator showing the whole structure; pick any node and continue from there.
  • /fork — branch from the current point into a parallel line of attack.
  • Retry a message — edit your last prompt and resend: a sibling branch, with the failed attempt preserved for comparison.
  • /resume — reopen any session at its leaf, days later.

If this feels like git — commits with parents, branches, HEAD — that's not analogy, it's the same data structure: a persistent tree grown by appending, with a movable pointer defining "current." One mental model, two tools you now understand.

The context problem branching creates

One subtlety keeps this honest. When you rewind past an assistant exchange, the model loses whatever it learned there — the abandoned branch isn't in the new path's context. Sometimes that's the point (the branch was poison); sometimes the branch did useful reconnaissance you'd hate to lose. pi's answer is branch summarization: on navigating away, it can ask a model to compress the abandoned branch into a branch_summary entry attached to the new path — "in a previous attempt, we tried X and learned Y." The knowledge survives at a fraction of the tokens. Notice the shape: summarize what you can't afford to keep verbatim. Hold that thought for one lesson — it's about to become the whole show.

Note · why trees beat undo

A linear undo stack destroys the redo branch the moment you type something new — everyone has lost work to that. Trees never sacrifice anything: every path taken remains reachable. The cost is conceptual (users must grasp "where am I in the tree?") and pi spends real UI effort (/tree's visualization, labels, summaries) paying it down. Data structures are UX decisions wearing a trench coat.

Branching = parentId + a leaf pointer + append-only discipline: git for conversations, with model-written summaries stitching knowledge across branches. Next, the pressure that makes summarization mandatory rather than optional: the context window fills, and something must give. Compaction.

Compaction: forgetting gracefully

Every long agent session marches toward the same wall: the conversation outgrows the context window. Compaction is how pi forgets on purpose — the real algorithm, with its real numbers, from core/compaction/compaction.ts.

When: two budgets

reserveTokens answers "when": compact once the conversation crosses window minus 16k — headroom for one more full response plus the summarization call itself. Trigger at 100% and you've already failed; the margin is the design. keepRecentTokens answers "how much survives": about 20k tokens of the newest turns stay verbatim, because recent context is what the model is actively working from.

And where does contextTokens come from? Not from counting words — from the provider's own usage report on the last assistant message (calculateContextTokens reads the Usage record from lesson 4.6, skipping error/aborted messages whose usage is garbage). The bill doubles as the fuel gauge.

Where: the cut point

The invariant hiding in that comment — never cut at a tool result — is load-bearing. Providers reject a conversation containing a tool result whose originating tool call is missing; slice carelessly and every future request 400s. Valid cut points respect the call/result pairing, and the walk-backwards loop (you saw it verbatim earlier: accumulate estimated sizes newest-first, stop at the budget, snap to the nearest valid cut) chooses among them. Structure-aware truncation, not scissors.

LLM · Summarization as memory

Every long-running LLM system needs a memory hierarchy, because attention is fixed and history is not. The emerging standard looks remarkably like an operating system's: recent turns stay verbatim (RAM), older history gets compressed into prose summaries (swap), and the full record lives on disk (cold storage), re-derivable but not resident.

Running TypeScript at runtime

Extensions are .ts files, and TypeScript famously needs compiling. Yet pi loads them instantly, with imports that resolve to packages the user never installed. Two tricks make it work — a type-stripping loader and virtual modules — and both repay understanding.

Trick one: jiti, the just-in-time loader

jiti is a library that imports TypeScript by transforming it on the fly — and here's where lesson 1.3's digression pays off: because pi's world restricts itself to erasable TypeScript (no enums, no namespaces — syntax that can simply be deleted), "transforming" is barely more than stripping the type annotations. No type checking happens at load time; types in extension files are for the author's editor. The runtime just wants the JavaScript underneath.

Node.js · Runtime module loading, vs importlib

Python people feel at home here: importlib.import_module() on a user's plugin file is a Tuesday. In compiled-language ecosystems it's exotic; JavaScript sits in between — dynamic import() of JS is native, but loading another language (TypeScript) requires a custom loader like jiti that hooks module resolution, transforms source, and evaluates it.

The knobs in the excerpt are the classic plugin-loader concerns, worth recognizing anywhere: cache control (moduleCache: false + pi's own cache with a generation token — so /reload actually reloads, defeating the module system's usual "import once" memoization; Python's importlib.reload scars apply), and resolution control — deciding what import "x" means inside a plugin. Which is trick two.

Trick two: the imports that shouldn't work

hello.ts began with import { Type } from "@earendil-works/pi-ai" — but the user writing that file in some random project never ran npm install @earendil-works/pi-ai. Resolution would fail… except pi intercepts it:

  • Dev/Node installs: an alias map points the pi package names at pi's own copies in its node_modules — extensions share the exact classes the host runs, so an instanceof or a TypeBox schema built in an extension is genuinely compatible.
  • Compiled binary installs: pi also ships as a single-file Bun executable with no node_modules at all. There, VIRTUAL_MODULES maps the import names to modules bundled inside the binary — imports resolved from memory, no filesystem involved.

Net effect: every extension gets a standard library — pi-ai's types, pi-tui's components, the agent core — "for free," and pi controls exactly which APIs that is. The import line in an extension is not a dependency declaration; it's a capability grant that happens to look like one. (Extensions needing genuinely external npm packages get a real package.json — the with-deps example — but the common case needs nothing.)

Why no build step is a feature, not laziness

The payoff compounds: edit .pi/extensions/foo.ts, type /reload, changed behavior — a seconds-long feedback loop. And one more consequence, the self-extensibility punchline: since the agent can write files (6.6), and extensions are just files, and the system prompt tells the model where the extension docs and examples live (7.4) — you can ask pi to write its own extensions, then /reload to activate them. Every piece of that loop is machinery you've now read; "self-extensible coding agent" turns out to be a precise technical claim, not marketing.

The component model

Last module of real code. pi-tui is a UI framework built on the humblest of foundations — a grid of characters — and its core abstraction is four members long. If you've ever wondered what React would look like reduced to its essence, this is the module.

The whole framework's contract

A component is anything that can answer: given this width, what lines are you? Not pixels, not boxes — an array of strings, one per terminal row, ANSI color codes included. Composition is then almost a joke:

Concatenate the children's lines. The screen — the TUI class itself — is a Container: pi's interactive mode is a list of message components, tool components, a spacer, and the editor, stacked. There is no layout engine, no flexbox, no absolute positioning; vertical stacking is the only layout, and everything else (columns, borders, padding) is a component formatting its own strings. Where the React instincts map — and where they don't

The big philosophical difference: no reactivity. Components are plain mutable objects; nothing tracks your state or re-renders "automatically." You change a field, you request a render. That's less magical than React and dramatically easier to debug — the entire mental model is "someone will call render() soon; return the right strings."

Caching matters because renders happen up to 60×/second while streaming. A chat message whose Markdown hasn't changed shouldn't re-tokenize itself every frame — components memoize their line arrays and rebuild only when their content changes (or when invalidate() announces a theme change or width-sensitive reset). render(width) being width-dependent is the subtle part: resize the terminal and every cache is stale, which is one reason resizes trigger the full-redraw path you'll meet next lesson.

The cursor trick

One puzzle a string-based UI must solve: the terminal has a single hardware cursor, and the focused editor needs it placed at the typing position (IMEs — for Chinese/Japanese input — draw their candidate windows there). But a component only returns strings… so the focused component embeds a zero-width marker — CURSOR_MARKER, an escape sequence terminals ignore — at its cursor position within its output. The TUI strips the marker during rendering and moves the real cursor to where it was found. In-band signaling, like a watermark: the component speaks only strings, yet communicates a coordinate.

The cast of components

With the interface this small, the library is really its component gallery: Text, TruncatedText, Input, SelectList, SettingsList, Loader/CancellableLoader (the spinners), Image (inline terminal graphics!), Markdown (lesson 9.6), and the 2,300-line Editor (lesson 9.5). Every chat bubble, diff view, and model-picker dialog you see in pi is one of these or a composition of them — and extensions register their own renderers into the same tree (8.1), because a component is just an object with render().

The differential renderer

TUI.doRender() is where strings become a smooth 60fps terminal UI. It's also a masterclass in a certain kind of engineering: a simple fast path, guarded by an honest list of cases where simplicity would lie.

Engineering · ANSI escape codes: the terminal as a canvas

A terminal is a character grid you draw on with escape sequences — byte strings starting with ESC (\x1b) that terminals interpret as commands instead of text. The handful this lesson needs: \x1b[3A / \x1b[3B move the cursor up/down 3 rows; \r returns to column 0; \x1b[2K erases the current line; \x1b[2J\x1b[H clears the screen and homes. Colors are the same idea (\x1b[31m = red) — which is why a component's "string" can carry styling.

The modern gem is synchronized output: \x1b[?2026h … \x1b[?2026l tells the terminal "hold all of this and apply it in one frame." Without it, a multi-write update can be displayed half-finished — that's what flicker is. Every buffer doRender emits is wrapped in this pair.

Throttling: before any drawing

The game-loop pattern: any number of "something changed!" calls collapse into at most one frame per 16ms. A model streaming fifty deltas a second costs fifty cheap boolean sets and ~60 actual renders, maximum. Note the last line — a request that arrives during a render isn't lost; it books the next frame.

The decision ladder

doRender renders the component tree to newLines, composites any overlays (dialogs), extracts the cursor marker — then walks a ladder from expensive-but-safe to cheap-but-conditional:

Read the comments — each guard is a documented war story. Width change: every wrapped line re-wraps, the diff would be garbage, redraw. Height change: same, except on Termux (Android), where the soft keyboard resizes the terminal constantly and a redraw-per-toggle would replay your whole scrollback — a shipping-on-phones bug you'd never anticipate from theory. This ladder is what production rendering code actually looks like: the algorithm is 20%, the guards are 80%.

The fast path: diff and repaint the window

previousLines is the entire trick: keep last frame's strings, compare with !== (string comparison — the "virtual DOM" is an array), find the changed window, move the cursor there with relative \x1b[nA hops, and rewrite only those rows. While the model streams prose, the window is typically one or two lines at the bottom: a repaint measured in tens of bytes. Over SSH on a bad connection, that's the difference between usable and unusable. One more honesty guard sits mid-path: if a change lies above the visible viewport (content scrolled), relative cursor moves can't reach it — full redraw. The fast path never guesses.

The bits we waved past: overlays, images, scroll bookkeeping

The real function also composites an overlay stack (modal dialogs painted over the base lines before diffing — the model picker is one), tracks Kitty-protocol inline images (which occupy multiple rows and must be deleted/redrawn as units — expandChangedRangeForKittyImages), and maintains viewport arithmetic (previousViewportTop, computeLineDiff) so cursor-relative moves stay correct as content scrolls. Plus a PI_DEBUG_REDRAW env flag that logs every full-redraw's reason to a file — the maintainers debug this code often enough to keep instrumentation in it.

What you now know

Fast terminal UI = throttle-and-coalesce, keep last frame, diff strings, repaint the changed window inside synchronized-output markers — and a ladder of honest full-redraw guards for every case where the diff would lie. Keyboard input, part 1: raw mode

Output was half the story. Input is the murkier half: keystrokes reach a program as an undifferentiated stream of bytes, batched unpredictably, with paste and typing indistinguishable — unless you negotiate. This lesson covers the plumbing from raw bytes to clean per-key events.

Entering raw mode (with an exit plan)

The moves, in order: remember the old state (a TUI that crashes without restoring cooked mode leaves the user's shell unusable — the classic "my terminal is broken" bug); flip to raw so every keypress arrives immediately, unbuffered, unechoed; then negotiate upgrades with the terminal — bracketed paste, Windows VT input, and the Kitty protocol (next lesson). Note that negotiation is literally writing escape codes to stdout and listening for the terminal's escape-code replies on stdin: the terminal is a peer you talk to, not a device you configure.

The batching problem, and StdinBuffer

Raw mode's catch: bytes arrive in arbitrary chunks. Type fast and one data event carries "abc"; an arrow key is the three bytes \x1b[A which may arrive split across two events; and a paste is one giant blob you must not interpret as typed commands (imagine pasting text containing q into something that quits on q…).

StdinBuffer (434 lines) is the fix — a small state machine that reassembles and splits the stream into one event per logical sequence: single keys, complete escape sequences, and paste blocks (delimited by the bracketed-paste markers we enabled above) emitted whole as a separate paste event. The 10ms timeout handles the genuinely ambiguous case: a lone \x1b might be the Escape key or the start of a longer sequence still in flight — wait a beat, then decide. Reassembly-with-timeout is the same shape as the SSE line-buffering you read in lesson 4.2; byte streams always need this dance.

Node.js · EventEmitter

StdinBuffer extends EventEmitter — Node's built-in pub/sub base class and the ancestral pattern of the platform. Mechanically it's a dict of listener lists: emitter.on("data", fn) appends, emitter.emit("data", seq) calls each listener synchronously. Python's closest kin are signal libraries (blinker) or hand-rolled callback lists; Node bakes it into the core (streams, sockets, and processes all are EventEmitters — you used one in lesson 6.5: child.stdout.on("data")).

Modern typed twist: EventEmitter<StdinBufferEventMap> — a generic event map so on("data", ...) and on("paste", ...) have typed payloads and a typo'd event name fails the build. Compare this to pi's other pub/sub, the Agent's awaited listeners (5.4): EventEmitter is synchronous fire-and-forget, fine for keystrokes; the Agent needed ordering and settlement guarantees, so it rolled its own. Choosing between those two is a recurring design decision, and now you've seen both sides of it in one codebase.

The routing chain

From TUI.handleInput, each clean sequence runs a gauntlet: terminal-protocol responses are consumed first (color queries, protocol negotiation — invisible housekeeping), then global input listeners get a veto (extensions can consume or rewrite input — lesson 8.1's input event), then the overlay stack (an open dialog captures keys before the world below), and finally the focused component's handleInput(data) — usually the editor. After any input, requestRender(). Notice there's no global keymap dispatching to actions; components interpret their own bytes, with a shared matchesKey helper for decoding. Which raises the question of how you match "ctrl+shift+p" against bytes at all — next lesson.

What you now know

The remaining mystery is the bytes themselves — why ctrl+shift+p needs a protocol upgrade to even exist.

Keyboard input, part 2: keys.ts

1,400 lines to answer "which key was pressed?" — because terminals encode keys in three generations of incompatible schemes. Along the way: the most dazzling type-level trick in the repository.

Why "which key?" is hard

The classic encoding is a fossil record. Printable keys arrive as themselves. ctrl+a through ctrl+z arrive as bytes 1–26 (that's why ctrl+c is byte 3, and why ctrl+i is literally indistinguishable from Tab — byte 9). Arrows and function keys are multi-byte escape sequences that vary by terminal. And whole categories simply don't exist: ctrl+shift+p, super+k, key release events — the wire format has no way to say them. Three fixes stack historically, and pi speaks all three:

  • Legacy sequences — the fossil layer, always available.
  • xterm modifyOtherKeys — an extension encoding modifiers numerically; the fallback.
  • Kitty keyboard protocol — the modern scheme (negotiated at startup, last lesson): every key event as an unambiguous CSI sequence with full modifiers and a press/repeat/release flag. This is why wantsKeyRelease exists on Component — hold-to-preview UI needs releases, which only Kitty can deliver.

parseKey/matchesKey normalize all three into one vocabulary, so components just write matchesKey(data, "ctrl+shift+p"). And that string argument is where TypeScript shows off.

The type that generates a keyboard

TypeScript · Template-literal types

TypeScript can compute with string types: `${M}+${Key}` is a type meaning "the string M, a plus, then Key" — and when M and Key are unions, the result is the union of every combination. This four-liner reads as a recursive comprehension: for each modifier M, produce "M+key", plus "M+" followed by any combination of the remaining modifiers (Exclude removes M, so "ctrl+ctrl+c" can't exist). Expanded, KeyId is a union of every valid combo — "c", "ctrl+c", "ctrl+shift+p", "ctrl+alt+super+f9" — thousands of strings the compiler enumerates so your editor can autocomplete them and matchesKey(data, "ctlr+c") fails the build on the typo.

Python's type system has nothing in this territory — Literal unions exist but can't be computed from each other. It's the clearest case in the course of TypeScript acting as a small proof engine over your string conventions. (Use sparingly: types this clever cost compile time and reader patience. Encoding a closed, mechanical grammar like key combos is the legitimate use.)

Keybindings: the indirection layer

One more floor sits above key identity: KeybindingsManager. Components don't ask "was that ctrl+z?"; they ask "was that the undo action?" — and a user-editable JSON file maps actions to KeyIds (remember AGENTS.md's rule from lesson 1.5: never hardcode key checks; add defaults to DEFAULT_EDITOR_KEYBINDINGS so they stay configurable — a law with an enforcement mechanism you've now met). Identity → vocabulary → binding → action: four layers between a byte and an undo, each testable alone.

Note · why 1,400 lines is the right size

Almost none of it is clever; it's coverage — every legacy sequence variant across terminal emulators, the full Kitty spec, Windows quirks, and a wall of regression tests next door (recall the TUI test directory's bug-regression-* files). Input handling is like the compat matrix of lesson 4.3: the world is inconsistent, so a complete map of it is bulky. The skill is keeping the bulk quarantined behind a two-function API.

What you now know

Key handling = three stacked wire protocols normalized into one typed vocabulary (generated by a recursive template-literal type), with a user-remappable binding layer on top. Now we can finally read the component that consumes most of these keys: the Editor.

The Editor

The box you type into is the largest component in the library — 2,300 lines. "It's just a text box" is the famous last words of UI engineering; this lesson tours why, and harvests two beautifully reusable sub-designs on the way.

Why a text box is never just a text box

Inventory what typing into pi actually requires, every piece implemented from scratch on the render(width) → string[] contract:

  • Multi-line editing with word-wrap — and wrap-aware cursor movement: "up" means visual line up, which after wrapping is not the same as logical-line up. The editor maintains a wrap layout (wordWrapLine, chunks) and a sticky preferred column, so cursoring through short lines and back remembers where you were. Every editor you've ever liked does this; you notice only when one doesn't.
  • Selection, kill ring, word navigation — Emacs-style ctrl+k/ctrl+y cut-and-recall (a KillRing class), alt+arrow word hops, all through the keybindings layer from last lesson.
  • Paste as an atomic unit — bracketed-paste events (9.3) insert as one segment: one undo step, no per-character re-render, no interpreting pasted newlines as submissions.
  • Autocomplete — the slash-command and file-path popup, debounced and cancellable (below).
  • Submit vs. newline — Enter submits (the onSubmit you traced in lesson 2.1), shift+enter inserts a line break… where the terminal can even tell the difference, which is a Kitty-protocol gift (9.4).

Harvest #1: undo as snapshots

Undo, the whole thing, in a class you can hold in one glance. The editor pushes a snapshot of EditorState (text + cursor) before each mutating operation; undo is pop(). structuredClone (a built-in deep copy, like Python's copy.deepcopy) makes snapshots immune to later mutation — the comment's "clone-on-push" discipline. Compare the alternative: command-pattern undo, where every operation implements an inverse. That's cleverer, saves memory, and breeds subtle bugs; snapshots are brute force that cannot be wrong. For editor-sized state, brute force wins. Generic over S, naturally — lesson 3.2's pattern, smallest possible edition.

Harvest #2: cancellable async autocomplete

The autocomplete popup has a hidden race: you type src/co, a filesystem scan starts; you type an m, a new scan starts — and if the old scan finishes last, stale results overwrite fresh ones. The editor's fix is the idiom you learned in lesson 5.3, at UI scale: each lookup gets an AbortController; the next keystroke aborts the previous controller before starting its own; results check their signal before touching the UI. Plus a debounce so a fast typist triggers one lookup, not eight. Abort the old, debounce the new, never trust a result without checking its signal — that trio solves every type-ahead race you'll ever meet, in any language.

The component discipline holds

For all its internals, the Editor exposes exactly the interfaces you already know: it's a Component (render(width) returns its box, prompt, wrapped text, and — when focused — the CURSOR_MARKER from 9.1) and a Focusable; input arrives via handleInput; the outside world sees onSubmit and a few setters. 2,300 lines of complexity, zero of them leaking into the contract. That's the whole art of components, demonstrated at the hardest difficulty setting the terminal offers.

Streaming Markdown

The last component closes the last gap in the Module 2 trace: the model's prose, arriving as raw Markdown fragments, becomes styled terminal text while incomplete. Rendering a format designed for finished documents, fifty times a second, mid-sentence — that's the trick.

The pipeline when nothing is moving

At rest, it's a textbook three-stage pipeline. The Markdown component wraps the marked library's lexer — one of pi-tui's two external dependencies (lesson 1.4), because a CommonMark tokenizer is exactly the kind of solved-problem bulk you buy rather than build. Marked turns text into a token tree (heading, paragraph, code fence, list…); pi's own renderer walks the tokens and emits ANSI-styled lines — bold, colors, indent for lists, syntax highlighting inside code fences via the theme system; and the result is, of course, just render(width) → string[]. Buy the parser, own the renderer: the renderer is where terminal-specific decisions live (how wide is a heading underline? what does a blockquote look like in text?), so that's the part worth owning.

The problem: Markdown mid-flight

Streaming breaks the textbook. Every text_delta (lesson 2.4) leaves the accumulated text in some torn state:

An unclosed bold, a dangling list item, and — worst — an unterminated code fence. Feed that to a naive parser and everything after ```typescript is "code," so the entire rest of the message renders as a code block until the closing fence arrives… then snaps back to prose. Multiply by fifty updates a second and you get strobing.

The fixes: tolerance, and stability

Two kinds of countermeasure, both instructive:

  • Heal the tear before parsing. Helpers like trimPartialClosingFences pre-process the partial text — treating a trailing unclosed fence as closed-for-now, so the half-written code block renders as a code block without swallowing what follows. The parse is of a lightly fictionalized document that looks like what the true document will become.
  • Keep rendered prefixes stable. The renderer's choices are biased so that already-emitted lines don't change when more text arrives — because stable lines are exactly what the differential renderer (9.2) rewards. If a delta only extends the last paragraph, only the last line or two of the component's output differ, and the repaint is tiny. The component and the renderer are co-designed around the same diff.

There's even a custom marked tokenizer subclass (a stricter strikethrough rule) — patching the parser's opinions where terminal reality disagrees. Wrapping a dependency and adjusting its behavior at the edges, rather than forking it: the adapter instinct (4.1), one last time.

Module 10 · Appendix: Frontiers & Next Steps

The other modes: print, JSON, RPC

Strip away the TUI and what's left? Everything, it turns out. The appendix begins with pi's three headless faces — culminating in RPC mode, where pi stops being a program you use and becomes a component other programs use.

print and json: pi as a Unix filter

pi -p "summarize the failing tests" runs one full agent session — loop, tools, everything — prints the final answer, exits. Pipe-friendly (lesson 6.1's TTY detection makes this automatic), so it slots into shell scripts, git hooks, and cron jobs: the agent as a 160-line mode (modes/print-mode.ts) over the same engine. --mode json is the same run, but emitting every event as a JSON line — the whole AgentEvent broadcast (2.2), serialized. Anything that can read lines can now watch an agent think.

RPC: the agent as a subprocess

RPC mode inverts the relationship: pi runs as a long-lived child process, commands arrive as JSON lines on stdin, and responses/events flow back on stdout. The command vocabulary is a discriminated union — of course it is — and reading it is a tour of everything you've learned, exposed as remote control:

Every command maps to an AgentSession method you already know — steer to the queue from 5.4, fork to the tree from 7.2, compact to 7.3. The optional id lets a caller match responses to requests over the shared pipe (concurrent commands in flight), and session events stream unsolicited between responses — the same broadcast, one more subscriber. Protocol design 101, and you've seen every ingredient: JSONL framing (2.7), discriminated unions (2.2), request/response correlation ids.

Why this matters more than it looks

RPC mode is what makes pi infrastructure. An IDE plugin, a CI bot, a web frontend, a test harness — anything that can spawn a process and speak line-JSON gets a full coding agent with sessions, tools, and extensions, no TypeScript required (a Python driver is a dozen lines of subprocess + json). It's also the enabler for the next lesson: if one pi can be driven through a pipe, many pis can be driven by a supervisor. The mode dispatch you met in lesson 6.1 turns out to be the load-bearing wall of pi's whole ecosystem strategy.

Go deeper (optional)

The full protocol — responses, event framing, lifecycle — is documented in packages/coding-agent/docs/rpc.md, with the implementation in src/modes/rpc/rpc-mode.ts (~800 lines) and a ready-made client class in rpc-client.ts.

What you now know

One engine, four faces: TUI for humans, print for pipes, json for observers, RPC for machines — each just a different subscriber to the same event broadcast, the payoff of a decision made back in lesson 2.2. Next: the experimental package that herds fleets of these subprocesses.

Module 10 · Appendix: Frontiers & Next Steps

The orchestrator

The fifth package — ~2,000 lines, boldly labeled experimental — asks the next question: if one agent is useful, what does managing a fleet of them look like? It's a preview of where the whole field is heading, built from parts you already understand.

The architecture: supervisor of subprocesses

The crucial design fact: the orchestrator does not embed the agent. It imports only the types — RpcCommand, AgentSessionEvent — and drives each pi through the same stdin/stdout protocol from last lesson, as an ordinary child process. Requests route by instance id; each child's event stream fans back to whoever is watching; instance records persist to a JSON file so the fleet survives supervisor restarts. If you've met process supervisors — systemd, supervisord, Kubernetes at a stretch — this is that shape, specialized for agents: spawn, health-check (a heartbeat/presence service called radius gives each instance a discoverable identity), forward, restart.

Engineering · Process supervision and IPC

Two classic patterns meet here. Supervision: a parent process owns children's lifecycles — spawn, monitor, restart on crash, reap on shutdown (the process-tree discipline from lesson 6.5, promoted to a whole program's purpose). IPC (inter-process communication): processes on one machine talking through OS channels — here local sockets carrying JSON, the plainest possible choice. Processes-plus-pipes beats threads-in-one-process for agent fleets on every axis that matters: isolation (a crashed agent can't corrupt its siblings), independent working directories and permissions, and language neutrality — the supervisor could be rewritten in Python tomorrow without touching pi. The cost is serialization overhead, which is noise next to LLM latencies. This is also, one layer down, exactly how your terminal, your shell, and pi itself already relate — Unix has been "orchestrating processes over pipes" for fifty years.

Why a fleet, and why "experimental"

The use case is visible in how pi's own maintainers work (remember AGENTS.md's rule about multiple pi sessions in one cwd, lesson 1.5): several agents running in parallel — one fixing a bug, one writing tests, one triaging issues — with a human sampling their streams. The orchestrator makes that a managed thing rather than six terminal tabs: spawn workers in the background, list them, attach to one, stop another.

And the label? The README warns the package may be removed — the honest marker of code exploring a design space rather than committing to one. Multi-agent supervision is where the industry is actively experimenting (who plans? who reviews? how do agents hand off?), and pi's contribution so far is deliberately minimal: get the plumbing right — spawnable agents, a clean wire protocol, presence — and defer the philosophy. Given how much machinery this course found under "just a loop," expect this space to grow the same way.

What you now know

The orchestrator = a process supervisor speaking last lesson's RPC protocol over local IPC, with persisted instance records and heartbeat presence — multi-agent infrastructure as a thin, honest layer over the subprocess design. One lesson remains: where to take everything you've learned.

Where to go from here

Fifty-eight lessons ago, pi was a magic trick. Now it's a machine whose every gear you've watched turn. This closing lesson takes stock of what you actually acquired — and where each thread leads if you pull it.

What you can now claim, honestly

  • You know how AI agents work — not vibes, mechanism: a stateless model, a conversation-as-list, tool schemas, a loop that feeds results back, streaming events, context budgets, compaction. When the next agent product launches, you'll recognize its skeleton before the demo video ends.
  • You can read a real codebase — you've practiced the actual skills: verify architecture at the import line (1.4), spot generated bulk (3.3), map a giant file by skeleton/thread/ callers (6.3), read a compat matrix as institutional memory (4.3), and treat tests and error patterns as documentation (4.4).
  • You own a stack of transferable patterns — discriminated unions + exhaustive switches, errors as values at boundaries, push-queues bridging callbacks and iteration, append-only trees, adapters and compat profiles, policy-free cores with injected hooks, fakes at the network seam, snapshot undo, abort-signal plumbing, diff-based rendering. Every one of these predates LLMs and will outlive them.

Threads worth pulling

  • Use pi seriously for a week. Every feature is now transparent: watch the footer's cost tick (4.6), fork a session (7.2), trigger /compact and read the summary it wrote (7.3), open the JSONL file afterwards (2.7). Using a system you understand is a different sport.
  • Write an extension. The gentlest real project: start from hello.ts (8.1), add a guard or a custom command for your own workflow. You know the whole API surface and can even ask pi to help — you understand exactly how it will (7.4 + 8.2).
  • Build a toy agent from scratch — in Python if you like. A hundred lines: a message list, one read_file tool with a JSON schema, a while loop over an LLM API. You'll hit, in miniature, every problem whose production solution you've now read — and that contrast is where the knowledge sets.
  • Follow the repo as it moves. pi ships fast (1.5); read a week of commits with git log in ~/Projects/pi and notice you can place every fix(ai): … in the architecture. Watching a living codebase evolve is the graduate course this one can't be.
  • Read the official docs as a peer. The ~30 files under packages/coding-agent/docs/ and the RFCs the README links now read as colleagues' notes rather than manuals.

The one-paragraph summary, for future you

An AI coding agent is a loop that alternates a stateless language model with validated tools, all speaking one normalized message vocabulary; adapters quarantine provider chaos below, an event broadcast fans state to UI, disk, and plugins above; context is the scarce resource everything budgets, caches, and compacts; and the product around the loop — sessions, trust, modes, extensions — is where most of the code and most of the craft lives. Everything else is detail, and you've read the detail.
