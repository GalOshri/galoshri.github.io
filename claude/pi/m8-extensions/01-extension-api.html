The extension system

pi calls itself "self-extensible": drop a TypeScript file in .pi/extensions/ and it runs inside the agent with access to nearly everything — no build step, no plugin SDK to install. This lesson maps the machinery; the simplest possible extension is our specimen.

An extension is a function

Read with Module-trained eyes, there's nothing new here: a TypeBox schema (3.2), an execute with the AgentTool signature — signal, onUpdate, content/details split (5.1) — and a default-exported factory function that receives the API object and registers things. That's the entire plugin contract: ExtensionFactory = (pi: ExtensionAPI) => void | Promise<void>. Twenty lines, and the model gains a tool that renders in the TUI and participates in the full lesson-6.7 lifecycle.

The API surface: five verbs

ExtensionAPI (defined in core/extensions/types.ts, ~400 lines of the file) groups into:

GroupMembersPower granted
observepi.on(event, handler) — ~30 typed eventswatch everything: session lifecycle, turns, messages, tool calls, provider requests, user input
intervenereturn values from handlersblock tool calls, rewrite results, replace the system prompt, transform context
add capabilityregisterTool, registerCommand, registerShortcut, registerFlagnew tools, slash commands, keybindings, CLI flags
actsendMessage, exec, setModel, setActiveTools, appendEntrydrive the agent: inject messages (steer/followUp — lesson 5.4's queues!), run processes, switch models
replace infrastructureregisterProvider, registerMessageRenderer, custom compactionswap the model backend or the UI rendering itself

The event map will feel familiar — agent_start, turn_end, tool_call, before_provider_request… — because you've seen where each one comes from. The extension runner (core/extensions/runner.ts) is the adapter between this registration surface and the hooks you've already read: it installs itself into agent.beforeToolCall / afterToolCall (5.3), transformContext and onPayload (6.2), and the AgentSession broadcast (2.2) — then fans each occurrence out to every subscribed extension, chaining their results. Extensions are loop hooks with a plugin manager. No new theory required; that's why this module is short.

Trust: the price of this power

An extension runs with pi's full process rights — your files, your environment variables, your credentials. Hence the trust gate from lesson 6.1: the first time you run pi in a directory, it asks whether to trust it; until then, project-local extensions do not load. The threat is concrete — git clone something && pi must not execute the something's code. Note the design's honesty: trust is binary and coarse (this directory: yes/no), not a permissions matrix pretending to sandbox TypeScript. If you need real confinement, the containerization docs (and Gondolin/sandbox example extensions) put the whole agent in a box instead.

What you now know

An extension is a default-exported function handed a capability object; the runner translates registrations into the hooks and broadcasts you've spent five modules reading; trust gates whose code gets this power. The genuinely novel part is the loading — TypeScript, at runtime, no build step. That trick is next.
