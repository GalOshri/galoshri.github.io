From pi to a running mode

Welcome to the product. pi-coding-agent is 51,000 lines — by far the biggest package — because products are where all the concerns live: settings, auth, trust, four different run modes. This lesson follows the boot sequence from the moment you type pi.

A thin entrance, a real hallway

The npm manifest maps the pi command to dist/cli.js — a 20-line stub whose only job is to call main(). The real orchestration is src/main.ts (~850 lines), and it reads like a checklist of everything a CLI product must do before any AI happens:

Two stops deserve comment. Migrations: pi versions move fast, and old settings files and session formats must upgrade in place — a product concern no tutorial ever mentions but every real CLI carries. Project trust: pi refuses to load a directory's extensions and run its commands until you've explicitly trusted that directory once. Why? Because a malicious repo could ship a .pi/extensions/steal-keys.ts that runs the moment you cd in and launch pi. Cloning code must not equal executing it (Module 8 returns to this).

Four modes, one decision function

The four personalities of the same agent:

ModeTriggerWhat it is
interactivedefault in a real terminalthe full TUI chat experience
print-p, or piped stdin/stdoutone prompt in, final answer out, exit — pi as a shell utility
json--mode jsonlike print, but emits the full event stream as JSON lines
rpc--mode rpca long-lived subprocess speaking a JSONL command protocol — pi as a component (Module 10)

The subtle line is !stdinIsTTY || !stdoutIsTTY: run git diff | pi -p "review this" and pi notices its stdin is a pipe, not a keyboard (a "TTY" — teletype — is Unix-speak for a real terminal), and downgrades itself to a well-behaved filter. Respecting pipes is what makes a CLI composable; it's the same check ls uses to drop its colors when piped.

Note · one engine, four faces

All four modes construct the same AgentSession (next lesson) and subscribe to the same event broadcast. Interactive renders events as UI; print discards all but the final message; json serializes each event; rpc forwards them to a parent process. The event-stream design from lesson 2.2 is what makes four products out of one engine — each mode is just a different subscriber.
