Anatomy of a tool definition

You've now read all seven tools. This closing lesson assembles the pattern they share — the full anatomy of a production tool — and replays one complete tool call with every layer you've learned switched on. Consider it the module's final exam, taken together.

The five organs

Every tool in core/tools/ has the same anatomy:

The last two organs are the ones this module hasn't dwelt on. Renderers: each tool ships functions that turn its calls and results into TUI components — read renders as a path with a line range, edit as a colored diff, bash as a live-scrolling output block. The tool owns its pixels; the chat view just asks. Prompt text: each tool contributes a snippet to the system prompt ("Available tools: …", next module) plus usage guidelines. A tool is therefore documentation for the model, UI for the human, and code — one module, three audiences, exactly the read/details split from lesson 5.1 grown to full size.

Structurally, each file exports a create<Name>Tool(cwd, options) factory (an AgentTool for the agent) and a create<Name>ToolDefinition variant — the extension-flavored wrapper that bundles the renderers and prompt text. Factories, not singletons: every session gets fresh tools bound to its working directory and its operations.

One tool call, replayed with everything on

The model decides to fix a typo. Follow the call through every layer you now own:

  • Wire: the adapter streams toolcall_start / toolcall_delta events; partial JSON is re-parsed each delta (4.2, 4.5) — the TUI is already rendering the forming call via the tool's renderer.
  • Grammar: toolcall_end delivers a parsed ToolCall { name: "edit", arguments: {...} } (3.4).
  • Loop: executeToolCalls → prepare: tool found, prepareArguments unwraps the model's quirks, TypeBox validates (5.3, 3.2).
  • Hooks: beforeToolCall fans out to extensions — a permission gate could veto here (6.2, 8.3).
  • Execute: the file-mutation queue admits the edit; exact match fails, fuzzy match lands it; line endings restored; a diff is computed (6.6).
  • Result: content (a terse "edited successfully" for the model) + details (the diff, for humans); afterToolCall gets the last word (5.3).
  • Broadcast: tool_execution_end + a ToolResultMessage — the TUI paints the diff, the session file gains a line, the cost ledger ticks (2.2, 2.7, 4.6).

Seven lessons ago that list would have been noise. Now every clause has a file behind it that you've read.

What you now know — and the module in one sentence

A production tool is a schema, swappable I/O, budgeted execution, self-rendering UI, and model-facing documentation in one factory — and pi's seven tools are that pattern instantiated for looking, running, and rewriting. Module 7 turns from what the agent can do to what it can remember: sessions, branching, compaction, and the construction of the system prompt itself.
