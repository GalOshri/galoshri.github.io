Mapping a 3,000-line file

agent-session.ts is 3,175 lines. interactive-mode.ts is 5,780. You cannot read files like these top to bottom — and professionals don't. This lesson teaches the actual technique, using agent-session.ts as the live specimen. It's the most transferable lesson in the course.

Rule zero: big files are maps, not novels

A novel punishes skipping; a map rewards it. Your goal with a huge file is never "read it" — it's to build a mental index good enough to answer: what does this thing own, what can you ask it to do, and where would my question live inside it? Three passes get you there, none of them linear.

Pass 1: the skeleton (five minutes)

Collapse the file to its structure — an editor's outline panel, or just searching for private , public , and method names. For AgentSession the skeleton comes out like this:

Ten clusters. The file is big not because any idea is big but because many small responsibilities meet here — which is exactly what "central object of a product" means. (Is that a God object? Somewhat — the maintainers accepted hub-ness at the seam between library and product. Note the trade rather than judging it.)

Pass 2: follow one thread (fifteen minutes)

Pick a question you actually care about and trace only its thread, ignoring everything else. Example: "how does a message reach the session file?" Search for subscribe — find that the constructor registers _handleAgentEvent with the Agent. Inside it, a familiar switch on event.type; the message_end case calls sessionManager.appendMessage(event.message). Done — that's the lesson 2.7 mystery, grounded, and you touched maybe 60 of the 3,175 lines. Each thread you pull adds a district to your mental map; three or four threads and the file feels navigable.

Pass 3: let the callers tell you what matters

Grep the codebase for session. — who calls what? You'll find the interactive mode calls prompt, abort, fork, tree navigation; the rpc mode calls nearly everything (it's a remote-control surface); extensions reach it through a facade. Caller frequency is a relevance ranking: the methods everyone uses are the file's true API, whatever its 30 private fields suggest.

Engineering · Reading code is search, not scanning

The uncomfortable truth about big codebases: nobody has read them. Their maintainers navigate by search and structure — outlines, go-to-definition, find-references, git blame — building just-in-time understanding for each task and letting the rest stay fog. Skill at "reading code" is mostly skill at asking narrow questions and refusing to read what doesn't answer them.

The three passes generalize anywhere: skeleton (what clusters exist), thread (trace one behavior end to end), callers (what does the world actually use). And a fourth for repos with history: git log --follow on the file — commit messages narrate why it grew. This is also, not coincidentally, how AI coding agents like pi read code: grep, read a slice, follow a reference. The technique is the same because the problem is the same — too much text, one question.

Note · why not split the file?

Reasonable question — and the team clearly knows how (they split everything else). A hub file has real advantages: one place to search, no artificial indirection, honest about its coupling. Splitting a hub into ten files often just hides the hub. The better metric than line count is can a newcomer build the skeleton quickly? — and thanks to consistent naming and clustering, here you can.

What you now know

Skeleton, thread, callers: three passes that turn any monster file into a map — 3,175 lines into ten labeled districts and a handful of traced routes. You'll use the technique immediately: the next three lessons walk into the tools directory, where the files are mercifully small but the details are sharp.
