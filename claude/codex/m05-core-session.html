core/ — Session, Thread, and Turn

codex-core is 180,000 lines across roughly a hundred files, several of them 80 KB or more. Opening it cold is genuinely intimidating. This module gives you a method for reading crates this size, then uses it on the four things that matter: who owns threads, how a submission becomes work, what the model is shown, and what happens when the conversation gets too long.

Mapping a crate this big

You cannot read core front to back, and you should not try. Here is what actually works, in order.

First, split code from tests. A large fraction of those files are test suites. codex-rs/core/src/mcp_tool_call.rs is 77 KB, but codex-rs/core/src/mcp_tool_call_tests.rs next to it is 99 KB. Any file ending _tests.rs can be ignored on a first pass — and its existence tells you the neighbouring file is important enough to deserve more test code than implementation.

Second, read the directory names, not the file names. core/src has fifteen subdirectories, and they partition the crate far better than the flat files do:

DirectoryWhat lives there
session/The session, the turn loop, the input queue, world state
tasks/Kinds of work: regular turn, compaction, review, user shell
tools/The tool registry, router, approvals, sandboxing glue
context_manager/Conversation history and what the model is shown
state/Mutable session state, task tracking
sandboxing/Applying the sandbox to a command
config/Config types owned by core
plugins/, guardian/, apps/Extension surfaces

Third, find the type that everything hangs off. In core that is Session, and its handle CodexThread. Follow those and the crate organises itself.

Engineering · Reading by public surface

The single highest-value command when meeting a big Rust file is to list its public items and nothing else — grep -n 'pub fn\|pub struct\|pub enum'. A 25 KB file might have eight public functions; those eight are the file's actual API and everything else is support. This works far better in Rust than Python because privacy is the default and pub is a deliberate act. It is how every excerpt in this module was found.

Note

You will notice pub(crate) on most things in core. That means "public inside this crate, invisible outside". So core's genuine external API — the part other crates can touch — is much smaller than it first appears. Anything pub(crate) is an internal detail you can read without worrying that the rest of the world depends on it.

ThreadManager: threads and their lifetimes

One process can have many conversations open. ThreadManager owns them all, and is deliberately thin:

Its public API is the vocabulary of thread management: start_thread, get_thread, list_thread_ids, update_thread_metadata, subscribe_thread_created. It also hands out the shared services every thread needs — auth_manager, mcp_manager, skills_service, plugins_manager — because those are expensive and belong to the process, not to any one conversation.

Rust · The leading underscore on a field

_test_codex_home_guard is never read. It exists to be dropped: when the ThreadManager goes away, that field's destructor runs and deletes a temporary directory. Rust's Drop is deterministic — it fires the moment a value goes out of scope, not whenever a garbage collector gets round to it — so "hold this value to keep a resource alive" is a standard idiom. Python's closest relative is a context manager, but here the scope is the with block. The underscore silences the unused-field warning and signals the intent.

Starting a thread takes an options struct rather than a dozen arguments:

initial_history: InitialHistory is the interesting field. A new thread starts with InitialHistory::New; a resumed or forked one starts with history read from a rollout file. Resumption is not a special code path — it is the same constructor with a different starting value, which is why codex resume and codex fork behave identically to a fresh session thereafter.

Go deeper (optional)

parent_trace: Option<W3cTraceContext> is distributed tracing plumbing — the same W3cTraceContext that appeared on Submission in Module 4. It lets a trace started in the IDE follow a request through the app-server, into core, and out to the model API. If you have used OpenTelemetry, this is that.

Engineering · A facade worth having

It is reasonable to ask why CodexThread exists if it just forwards. Because it is the boundary: Session and SessionIo are internal and change freely, while CodexThread's surface is what app-server depends on. The forwarding methods are the price of being able to restructure everything behind them without breaking a consumer. Notice also that the fields are pub(crate) — inside the crate the facade can be bypassed; outside it cannot.

Beyond the two queue methods, the surface tells you what a client legitimately needs: steer_input (interject mid-turn), try_start_turn_if_idle, inject_response_items, token_usage_info, list_background_terminals, terminate_background_terminal, flush_rollout, shutdown_and_wait.

That steer_input is the mechanism behind has_pending_input from Module 3's loop. And the background terminal methods reveal something the UI hints at: a shell command can outlive the turn that started it, so someone has to be able to list and kill them.

Rust · Why the same trait twice

-> impl Future is the efficient form: each implementation returns its own concrete future type, with no allocation. But a trait using it cannot be turned into dyn Trait — and the session needs to store "some task" without knowing which. So AnySessionTask is the type-erased twin returning a BoxFuture (a heap-allocated future, exactly the Pin<Box<dyn Future>> from Module 2), with a blanket implementation bridging every SessionTask to it. Authors write the ergonomic trait; the session stores the erased one. Remember AGENTS.md: "Prefer native RPITIT trait methods with explicit Send bounds" — this is that rule, with its consequence.

The context manager

The model does not see the conversation. It sees whatever context_manager decides to render. That distinction is the whole subject.

The history's internal API divides cleanly into recording, measuring, and rendering:

MethodPurpose
record_items(items, policy)Append, applying a TruncationPolicy
for_prompt(input_modalities)Render what the model will actually receive
raw_items() / into_raw_items()The unfiltered truth
estimate_token_count(ctx)How big is this conversation?
get_total_token_usage(...)What did we actually spend?
remove_first_item(), drop_last_n_user_turns(n)Forget, from either end
replace(items)Swap the whole history — how compaction lands

for_prompt is the one to hold onto. Module 3 saw it called:

Two things happen here. The history is cloned, so the rendering cannot mutate the record. And it is filtered by input_modalities — if this model cannot accept images, the images are dropped from what it is sent, while staying in the stored conversation. Switch to a vision model mid-thread and they reappear.

LLM · Why history is rebuilt every call

Language models are stateless. Each request carries the entire conversation again — there is no server-side memory of your last message. That is why for_prompt runs on every iteration of the loop, why token counts grow superlinearly with turn count, and why the context window is a hard wall rather than a soft one. Everything in the next section follows from this single fact.

remove_first_item and drop_last_n_user_turns are the crude instruments — drop from the front, or roll back whole turns from the end. replace is the surgical one, and it is what compaction uses.

Compaction: forgetting gracefully

When a conversation approaches the context window, Codex asks the model to summarise it, then replaces the history with that summary. The conversation continues; its early detail does not.

Note the framing: not "summarise this conversation" but "write a handoff for another LLM that will resume the task". Compaction is treated as a shift change, and the prompt optimises for whoever picks up the work.

Rust · include_str!

Reads a file at compile time and embeds its contents as a &'static str in the binary. The prompt is editable as Markdown by anyone, with no build step and no runtime file I/O to fail. This is why codex-rs/prompts/templates/ is worth browsing: it is every instruction Codex gives a model, in plain text.

And there are sibling files — codex-rs/core/src/compact_remote.rs, codex-rs/core/src/compact_remote_v2.rs, codex-rs/core/src/compact_model_fallback.rs — because summarisation can also happen server-side, and because the model you were using might not be available to do it.

Compaction is not silent. It emits an event and leaves a permanent item in the transcript — EventMsg::ContextCompacted and TurnItem::ContextCompaction from Module 4 — so both you and the rollout file know a memory was lost and when.

Even this has extension points: hooks run before and after compaction, so a plugin can save state that is about to be forgotten. Module 11 covers hooks.

Why does compaction have its own analytics vocabulary?

compact.rs imports CompactionPhase, CompactionReason, CompactionStatus, CompactionStrategy, CompactionTrigger, and CompactionImplementation from codex-analytics. Six separate dimensions of telemetry for one operation. That is a strong signal: compaction is a place where quality quietly degrades, and if it fires too early, too often, or drops the wrong things, users experience it as "the agent got dumber" without knowing why. You cannot debug that from a bug report — only from aggregate data.

What you now know

Read a big crate by ignoring _tests.rs files, reading directory names, listing public items, and finding the central type. ThreadManager owns threads and the process-wide services; CodexThread is a deliberately thin facade over Session plus two queues; tasks are a small trait with a type-erased twin; the context manager rebuilds the model's view on every call and filters it by what the model can accept; and compaction replaces history with a handoff summary, loudly, with hooks and heavy telemetry.
