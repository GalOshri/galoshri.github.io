The Other Front Doors

Module 9 covered the front door with a human behind it. This module covers everything else that drives the same agent: shell scripts, IDE extensions, the desktop app, other AI tools, two SDKs, and the cloud. The recurring idea is that none of them is a special case.

codex exec: the non-interactive mode

codex exec "fix the failing test" runs a turn with nobody watching: no TUI, no approval prompts, output to stdout, exit code that means something. It is the mode you put in CI.

Module 3 read its loop. The point worth returning to is what it doesn't do differently:

Same InProcessServerEvent, same app-server protocol as the TUI. The difference is entirely in the event_processor, and there are two of them: codex-rs/exec/src/event_processor_with_human_output.rs and codex-rs/exec/src/event_processor_with_jsonl_output.rs.

One prints prose for a person reading a CI log; the other prints one JSON object per line for a program. Same events, two renderings — which is exactly the separation that made into_response and code_mode_result coexist in Module 7.

Engineering · JSONL as a machine interface

JSON Lines — one complete JSON value per line — is the standard shape for streaming structured output from a CLI. It is greppable, it can be consumed incrementally without a streaming parser, and a truncated stream still yields every complete record before the cut. If you want to script Codex, this is the surface to target, and Module 4's EventMsg is its vocabulary.

Notice error_seen being threaded through both branches in that loop. Getting the exit code right is most of what separates a tool you can put in CI from one you cannot, and Module 4's distinction between Interrupted and Failed is what makes it possible.

app-server: the JSON-RPC daemon

This is the crate everything else routes through — 44,000 lines, with 29,000 more in its protocol crate. Modules 1 and 3 established the surprise: the TUI and exec are already clients of it, in-process.

Rust · Crate-level attributes

#![...] with the exclamation mark applies to the enclosing item — here, the whole crate — rather than the item below it. deny(clippy::print_stdout) makes any println! anywhere in these 44,000 lines a compile error.

That is not stylistic. When the app-server runs as a subprocess, stdout is the protocol channel. A stray println!("here") left in during debugging would inject garbage into the JSON-RPC stream and break the IDE extension in a way that is maddening to diagnose. So the compiler forbids it, and logging goes to a file or to stderr through tracing.

There is a family of crates around it, and the split tells you the shape of the problem:

CrateRole
app-serverThe server: holds threads, translates requests into Ops
app-server-protocolThe types (Module 4's macro table)
app-server-clientThe client half — InProcess or Remote
app-server-transportFraming over stdio, sockets, or a Unix domain socket
app-server-daemonLifecycle: start, stop, discover a running server
app-server-test-clientA test harness that drives a real server

Transport is a separate crate because the same protocol runs over stdio (IDE extension spawning a subprocess), a Unix domain socket (the desktop app talking to a shared daemon), and in-process channels. Hence codex-rs/uds and codex-rs/stdio-to-uds — the latter being the hidden subcommand from Module 1, a shim for clients that can only speak stdio when the server is on a socket.

Engineering · Dogfooding the boundary

The decision to make the TUI a client of app-server rather than calling core directly costs a serialisation boundary and a layer of indirection in the most latency-sensitive path in the product. What it buys is that the IDE integration can never be a second-class citizen: every feature the terminal has must be expressible in the protocol, because the terminal has nothing else. Bugs in the protocol surface immediately for the people who work on Codex daily, instead of being reported months later by extension users.

Codex as an MCP server

codex mcp-server exposes Codex to other AI tools. Another agent — Claude Code, an IDE assistant, a custom orchestrator — connects and gets Codex as a tool it can call.

The crate is small, which is the interesting part: codex_tool_config.rs, codex_tool_runner.rs, message_processor.rs, exec_approval.rs, patch_approval.rs. Codex is presented as essentially one tool:

One tool — "run a Codex session" — parameterised by the same Config fields a human would set. Note that the calling agent chooses the approval-policy, which means it can grant itself never. The sandbox remains the actual boundary; Module 8's insistence that auto-approval requires a real cage is what makes this safe to expose at all.

exec_approval.rs and patch_approval.rs exist because approvals must still work when the "user" is another program. MCP has an elicitation mechanism for a server to ask its client a question, and these map Codex's approval requests onto it — the same ServerRequest pattern from Module 3, in a third dialect.

Codex as an MCP client

The mirror image: codex-rs/rmcp-client (~11,000 lines) connects out to MCP servers you configure, and codex-rs/codex-mcp manages those connections. Their tools become tools the model can call, indistinguishable from built-ins at the point of use, as Module 7 showed.

So Codex sits on both sides of the same protocol. A single machine can run Codex exposing itself over MCP to one agent while consuming three other MCP servers itself. codex mcp — the subcommand from Module 1's list — is how you manage the ones it consumes.

Note

Two crates, two directions, similar names: codex-rs/mcp-server is Codex being a server; codex-rs/rmcp-client is Codex being a client; codex-rs/codex-mcp holds the shared connection management that AGENTS.md tells contributors to route changes through.

The Python and TypeScript SDKs

sdk/ holds three things: python/, python-runtime/, and typescript/. The TypeScript package is @openai/codex-sdk, and its module list is the API:

codex, thread, turn, events, items — the exact vocabulary of Module 4, in TypeScript. That is not a coincidence or a convention someone maintains by hand. Recall the TS derive on every protocol type in Module 2, and export_client_param_schemas in Module 4's macro: these types are generated from the Rust.

Both SDKs work by driving the compiled binary — the exec.ts module is the giveaway. You are not reimplementing the agent in another language; you are speaking the app-server protocol to a subprocess. Which is why python-runtime/ exists: something has to locate and manage that binary.

SDK · Why subprocess rather than a library binding

You could bind Rust into Python with PyO3 and skip the process boundary. The subprocess approach wins for a coding agent: the SDK ships as pure Python with no compilation, the agent's crashes cannot take down your process, the sandbox is applied to a child that is already separate, and the same binary serves every language. The cost is serialisation on every message — which is already being paid, because the TUI does the same thing.

codex-cli/ at the repository root is the third distribution path: an npm package containing bin/, scripts/, and a package.json, which downloads the right native binary for your platform. That is what npm install -g @openai/codex installs — a downloader, not a JavaScript implementation.

Codex Cloud

The last front door runs somewhere else. Codex Web executes tasks on OpenAI's infrastructure, and this repository holds the client: codex-rs/cloud-tasks, cloud-tasks-client, cloud-tasks-mock-client, and cloud-config.

app.rs, ui.rs, scrollable_diff.rs — this is another terminal UI. codex cloud gives you a browser for tasks running in the cloud, with a diff viewer to review what they changed before applying it locally. Module 1's codex apply subcommand is the other half: take the diff a cloud task produced and git apply it to your working tree.

cloud-tasks-mock-client being a full crate is worth noting. Testing against a real cloud service is slow, flaky, and requires credentials, so the client is defined by a trait with two implementations — the same fake-the-boundary pattern as TimeProvider in Module 2, scaled up to an entire service.

What you now know

codex exec is the same event loop as the TUI with a different renderer, and JSONL is its machine surface. app-server is the hub every front door goes through, with stdout so sacred that printing to it is a compile error, and a family of crates splitting protocol from transport from lifecycle. Codex is both an MCP server and an MCP client. The two SDKs drive the compiled binary as a subprocess and their types are generated from the Rust, so the Python you read in Module 1 is a direct projection of Module 4's protocol. And codex cloud is a terminal client for agents running elsewhere.

What remains is everything that persists between runs, and everything that lets you change Codex's behaviour without forking it.
