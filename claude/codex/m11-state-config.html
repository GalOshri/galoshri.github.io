State, Config & Extension

Everything so far described a single run. This module is about what survives between runs — configuration, conversations, project knowledge — and about the five separate mechanisms Codex provides for changing its behaviour without touching its source.

config: layers, profiles, overrides

Configuration is not a file. It is a stack of layers, each knowing where it came from:

And precedence is an explicit number, not an implicit ordering:

Read it bottom-up from 0: MDM is the base, then system, then enterprise bundle, then your config.toml, then your selected profile, then the project's .codex folder, then flags you typed. Nearer the user wins. The two legacy layers at 40 and 50 sit above everything — deliberate compatibility scaffolding so an older managed-config mechanism keeps overriding as it always did.

The gap between 20 and 21 is the neatest detail here: a profile is not a separate kind of layer, it is your own config at one point higher precedence, so --profile work overrides your defaults and nothing else changes.

Engineering · Keep the provenance

The naive approach merges everything into one struct at startup and forgets where each value came from. Then "why is my model setting being ignored?" becomes unanswerable. Codex keeps each layer as a ConfigLayer with its name, version, and even a disabled_reason — which is why codex-rs/config/src/diagnostics.rs and the codex doctor subcommand can tell you exactly which file won.

Because config is layered and typed, it is also schema-generated. Remember AGENTS.md: "If you change ConfigToml or nested config types, run just write-config-schema" — producing codex-rs/core/config.schema.json, the authoritative list of every setting.

Rollouts: how conversations persist

A rollout is the on-disk record of a thread. Module 3 established that events go to your screen and to a file at the same time; this is that file, and the crate around it is bigger than you would expect:

Module in rollout/Problem
recorder.rsAppend events as they happen
reverse_jsonl_scanner.rsRead a JSONL file backwards
compression.rsOld rollouts get large
session_index.rs, rollout_reference_index.rsFind a conversation without reading every file
search.rs, list.rsBack the codex resume picker
state_db.rs, sqlite_metrics.rsAn SQLite index alongside the files
policy.rsWhat to keep, what to discard

Engineering · Why append-only, and why read backwards

Appending one JSON object per line is crash-safe by construction: a process killed mid-write loses at most the last line, and everything before it is still valid. Nothing is ever rewritten, so there is no window where the file is inconsistent. The cost is that the most interesting information — how the conversation ended, what it was about — is at the far end. Hence reverse_jsonl_scanner.rs: to list your recent sessions, read each file backwards and stop early, rather than parsing megabytes to reach the last line.

Module 5's InitialHistory is the other end of this. Resuming replays a rollout into a new thread; forking replays it and diverges. Both are ordinary thread construction with a non-empty starting history, which is why resume, fork, archive, unarchive, and delete could all appear in Module 1's subcommand list without any of them being a special case.

codex-rs/rollout-trace is a separate 13,000-line crate for replaying a recorded session — the replay_bundle and REDUCED_STATE_FILE_NAME imports you saw in codex-rs/cli/src/main.rs back in Module 1. A bug report can ship as a bundle that reproduces the exact sequence of events.

AGENTS.md and project context

Codex reads instructions from your repository. The algorithm is documented at the top of the file that implements it:

Every AGENTS.md between the project root and where you are, in order, concatenated — so a monorepo can have a general file at the top and a specific one in each package. Rule 3 is the safety property: Codex will not climb into your home directory and pick up instructions from an unrelated project.

This is why tui/src/bottom_pane/AGENTS.md exists as its own file in Module 9. Work in that directory and you get the general rules plus the composer-specific ones.

AGENTS.override.md is for personal instructions you do not want to commit. And MAX_CONCURRENT_ANCESTOR_PROBES is a reminder of the scale this runs at: directory probing is done concurrently, bounded, because on a network filesystem an unbounded fan-out would be its own outage.

LLM · Instructions are still just context

Everything assembled here is prepended to the conversation as text. It costs tokens on every request, competes for the model's attention with your actual question, and — as Module 8 warned — is not privileged over anything else the model reads. A 500-line AGENTS.md is not five times better than a 100-line one; it is five times more expensive and probably less well followed.

Skills and prompts

codex-rs/prompts/templates/ is worth browsing whole: it is every instruction Codex gives a model, as plain Markdown, embedded with include_str!. You have already read two — compact/prompt.md in Module 5 and apply_patch_tool_instructions.md in Module 7. Others cover review rubrics, goal tracking, and realtime sessions.

Skills are the user-supplied version of the same idea: reusable, named instructions Codex can load on demand, with their own crates (codex-rs/skills, codex-rs/core-skills). Because a skill can depend on an MCP server being available, there is a codex-rs/core/src/mcp_skill_dependencies.rs to resolve that.

The design constraint is the same one behind tool_search in Module 7: instructions loaded eagerly cost tokens forever, so skills are discovered and injected only when relevant.

Hooks and plugins

Two different extension mechanisms, and the difference matters.

Hooks are callbacks at defined lifecycle points. The crate's structure shows the shape — declarations.rs, registry.rs, config_rules.rs, an events/ directory and an engine/ directory. You met them in Module 5 wrapping compaction (run_pre_compact_hooks, run_post_compact_hooks), and in Module 3 as run_hooks_and_record_inputs inside the turn loop. Module 7's post_tool_use_payload on the tool trait is a hook point too.

output_spill.rs is a good detail: a hook is often an external program, and an external program can print more than you want in your context window, so its output has to be capped and spilled. Extension points are only safe if they are bounded.

Plugins are heavier: codex-rs/plugin, codex-rs/core-plugins (~36,000 lines — the fourth largest crate in the repo), and codex-rs/ext with sub-crates including extension-api, agent, connectors, goal, guardian, image-generation, items, and memories.

This is where Module 4's TurnItem::Extension pays off — the variant whose "schema and lifecycle details are owned by an extension". A plugin can introduce a new kind of item that core stores, persists to the rollout, and forwards to clients without understanding it. That is a real extension point rather than a callback.

Module 7's request_plugin_install and list_available_plugins_to_install tools close the loop: the model can notice it lacks a capability and ask to install it. Together with codex plugin and codex marketplace from the CLI, this is a distribution system, not just an API.

Engineering · Five ways to extend, on purpose

Config changes settings. AGENTS.md adds instructions. Skills add reusable instructions on demand. MCP adds tools from other programs. Hooks run code at lifecycle points. Plugins add items, tools, and behaviour. That looks like duplication, but each targets a different author — a user, a repository, a team, a tool vendor, an ops engineer, a developer — and collapsing them would force everyone up to the most powerful and most dangerous mechanism.

Memories, telemetry, analytics

Memories (codex-rs/memories, ext/memories, core/src/memory_usage.rs, protocol/src/memory_citation.rs) let facts persist across threads — not just within one conversation. The memory_citation type is the honest part: when a memory influences an answer, it can be cited, so you can see why Codex believed something. Module 6's summarize_memories on ModelClient is where they get condensed.

Telemetry splits in two, and the split is deliberate. codex-rs/otel is OpenTelemetry — traces and spans for debugging, the .instrument(trace_span!(...)) calls threaded through Module 3's turn loop and the W3cTraceContext on Submission in Module 4. It answers "what happened in this request, and where did the time go?"

codex-rs/analytics is product measurement, and Module 5 showed how granular it gets — six separate enums describing a single compaction. It answers "is this feature making things better or worse across everyone?"

Note

codex-rs/response-debug-context and core/src/prompt_debug.rs are the tools for the question you will eventually have: what exactly did the model receive? After Module 5's context manager, compaction, injected skills, and assembled AGENTS.md, the answer is genuinely hard to reconstruct by reading code. Both exist because the authors needed them.

What you now know

Config is a precedence-ordered stack of layers that remembers where each value came from, with profiles as a one-point bump over your own defaults. Rollouts are append-only JSONL, read backwards for speed, indexed in SQLite, and replayed to resume or fork. AGENTS.md is concatenated from the project root down and never above it. Prompts and skills are Markdown, loaded lazily because context is scarce. Hooks are bounded lifecycle callbacks; plugins can introduce item types core does not understand. And Codex measures itself twice — traces for debugging one request, analytics for judging a feature.
