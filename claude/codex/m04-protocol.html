protocol/ — The Shared Vocabulary

Before any crate can do anything interesting, they all have to agree on what a message, a turn, and a command execution are. That agreement is a crate of its own — about 22,000 lines that contain almost no logic and are depended on by everything. This is the dictionary for the rest of the course.

Two things are worth pausing on. Interrupt's doc comment names the event it produces — the protocol documents its own request/response pairs inline. And ExecApproval being an Op means approving a command is a submission just like typing a message. There is no side channel for approvals; they queue up with everything else, which is why ordering is preserved.

The reply side is EventMsg, and its variants read like a transcript of everything that can happen:

Notice the Begin/End pairing on everything slow, with a Delta in the middle where output streams. That is a deliberate, repeated shape: any operation that takes time announces its start, streams its progress, and announces its finish, so a UI can draw a spinner and fill it in without special-casing each operation.

Engineering · Errors are events, not exceptions

Error(ErrorEvent) is a variant like any other. A failed turn does not blow up a call stack — it emits an event, gets recorded in the rollout, and appears in your transcript. Tomorrow you can resume that thread and the model will see what went wrong. This is the same instinct as Rust's Result from Module 2, applied one level up: failure is data.

Note

EventMsg carries a warning in its doc comment: "Make sure none of these values have optional types, as it will mess up the extension code-gen." Protocol types are compiled into TypeScript for the IDE extension, and an Option in the wrong place produces a type the generator can't express. The protocol is shaped by its consumers.

The item model

Events describe things happening. Items describe things that exist — the durable contents of a conversation. If events are a live commentary, items are the scorecard.

This is the list you saw in the Python SDK in Module 1 — result.items, and root.type == "agentMessage". The same enum, serialised to JSON.

Read it as an inventory of everything Codex can produce. A turn is not just "the model said something"; it may include a plan, private reasoning, several command executions, file changes, MCP tool calls, and a note that the context had to be compacted halfway through.

Rust · skip_serializing_if

Serde attributes control the JSON shape without changing the Rust type. skip_serializing_if = "Option::is_none" means "omit this key entirely when there's no value", rather than emitting "client_id": null. #[serde(default)] is the mirror image on the way in: a missing key becomes None instead of a parse error. Together they are how a protocol stays backward-compatible while gaining fields.

Two representations, one truth

Notice Extension(ExtensionItem) and the comment on it: "Item whose schema and lifecycle details are owned by an extension." The item model is deliberately open — a plugin can introduce an item type that core stores and forwards without understanding. Compare it with the note on WebSearch:

Two paths to the same user-visible feature: one where the model provider runs the search and core knows the shape, one where a Codex extension does it and owns its own schema. That kind of duplication is the honest cost of supporting both hosted and local capabilities, and this codebase documents it rather than hiding it.

Turns, threads, and their states

Identifiers get their own files and their own types, rather than being loose strings:

Rust · Newtypes

Wrapping a Uuid in a one-field struct costs nothing at runtime and buys a compile error if you ever pass a SessionId where a ThreadId was wanted. In Python both would be str and the mix-up would be a runtime mystery. #[ts(type = "string")] tells the TypeScript generator to flatten it back to a plain string on the wire — the type safety is for Rust's benefit, not the protocol's.

The comment "some use cases rely on that" is load-bearing. UUIDv7 embeds a timestamp and sorts chronologically, so sorting thread ids sorts threads by creation time — no separate index needed.

app-server-protocol: the JSON-RPC dialect

Recall from Module 3 that the TUI does not speak Op/Event — it speaks a JSON-RPC protocol to an app-server, which then speaks Op/Event to core. That outer protocol is a separate 29,000-line crate.

The interesting part is how it is defined. Not as a hand-written enum, but as a table fed to a macro:

Rust · Declarative macros

macro_rules! defines a macro that matches syntax patterns and expands to code at compile time. It is not string substitution like C's #define, and it is not runtime metaprogramming like Python's decorators or type() — the expansion happens before type checking, and the result is ordinary code the compiler verifies. When you see something! { ... } with a body that doesn't look like Rust, you are reading a domain-specific language someone defined a few hundred lines above.

One entry in that table generates, at minimum: a ClientRequest enum variant, the JSON-RPC method string "thread/start", the matching ClientResponse variant, a TypeScript type, and a JSON Schema file. You can see the generators in the same macro:

The $( ... )* is macro repetition — "do this once per entry in the table". stringify!($params) turns a type name into a string literal at compile time.

Engineering · One source, many artefacts

This is the pattern worth taking away from the whole module. There is exactly one place where "what requests exist" is written down. The Rust enum, the wire method names, the TypeScript SDK types, and the published JSON schemas are all derived from it. Nothing can drift, because there is nothing to keep in sync. The cost is that the definition is a macro invocation rather than plain code — harder to read once, impossible to get wrong afterwards.

Why v1 and v2?

Look again at that table: Initialize takes v1::InitializeParams, while the thread operations take v2:: types, under a comment reading /// NEW APIs. Both versions are live simultaneously.

This is the tax of shipping a protocol other people depend on. An IDE extension installed six months ago still speaks v1, and it must keep working. A protocol crate makes that tax visible and manageable: versions sit side by side in one table, and inspect_params flags requests where only some fields are experimental.

Why a protocol crate exists

It is fair to ask why 22,000 lines of type definitions deserve their own crate rather than living in core. Four reasons, all visible in what we just read.

It breaks dependency cycles. tui, exec, app-server, and core all need these types. If they lived in core, then core would be a dependency of everything and nothing could be tested without it. Recall the technique from Module 1 — read the Cargo.toml: codex-protocol appears in nearly every crate's dependency list, and it depends on almost nothing itself.

It is the code-generation source. The TypeScript SDK and the JSON schemas are generated from these types. That requires a crate you can compile and run generators over without dragging in the entire agent.

It makes the boundary reviewable. A change to protocol/ is a change to a contract with external consumers, and it shows up as such in a diff. A change buried in core would not.

It is where the vocabulary is documented. The doc comments in this crate — "this Op sends that EventMsg in response", "Codex-generated thread IDs are UUIDv7", "make sure none of these values have optional types" — are the closest thing to an architecture document the repository has.

What you now know

Op is everything a client can ask for and EventMsg everything that can happen, paired by a correlation id, with Begin/Delta/End for anything slow and errors delivered as data. TurnItem is the durable inventory of what a turn produced, open to extension. Identifiers are newtypes, not strings. The outer JSON-RPC API is generated from a single macro table that also emits TypeScript and JSON Schema, with v1 and v2 coexisting deliberately.
