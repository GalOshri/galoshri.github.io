core/ — Talking to the Model

client.rs is 96 KB — the largest single file in core. All of it exists to turn "here is a conversation" into "here is a stream of things the model decided", reliably, across providers, over a network that fails. This module is where the abstraction meets the wire.

Read the parameters as the anatomy of a model call. prompt is the conversation. model_info is which model and what it can do. effort and summary control reasoning — how hard to think, and how much of that thinking to show you. service_tier selects a latency/price tier. The last two are telemetry.

One wire API

A one-variant enum is an unusual thing to find, and it tells a story: Codex used to speak Chat Completions as well, and no longer does. The enum survives as a seam — the dispatch site still matches on it, so adding a second wire format is a local change rather than an archaeology project.

LLM · Responses vs Chat Completions

Chat Completions is the familiar list of {role, content} messages. The Responses API is item-based: the conversation is a sequence of typed items — messages, reasoning, function calls, function outputs — which is why TurnItem in Module 4 looks the way it does. Crucially it can carry reasoning items between turns, so a model's private chain of thought survives a tool call instead of being thrown away. For an agent that makes many calls per turn, that is the difference between thinking once and re-thinking every time.

Streaming: SSE to events

stream returns a ResponseStream, which yields ResponseEvents. That enum is the wire protocol of a model call:

Same Added/Delta/Done discipline as the EventMsgs in Module 4, one layer down. Note ToolCallInputDelta: even the arguments to a tool call stream in character by character, which is how a UI can show "running cargo test…" before the model has finished typing the command.

The comment on end_turn is the most valuable line in the enum:

Did the model affirmatively end its turn? Some providers do not set this, so we rely on fallback logic when this is None.

This is the origin of needs_follow_up from Module 3's loop. Ideally the model says "I'm done". When the provider doesn't report it, Codex infers it — did the model request a tool? did it produce a message? — because the loop must terminate either way.

Wire · Server-sent events

SSE is a one-way streaming format over ordinary HTTP: the server holds the response open and writes data: {...} lines separated by blank lines. No WebSocket handshake, no framing protocol — it survives proxies and corporate networks that block everything else. Each line is a JSON chunk that Codex parses into one ResponseEvent. That said, Codex also supports a WebSocket transport for the Responses API, with an explicit fallback.

Try the WebSocket; if it reports FallbackToHttp, record that decision on the session and use SSE instead. Because the decision lives on ModelClientSession, one failed handshake doesn't cause a retry storm — the rest of the turn goes straight to HTTP. That is exactly the per-turn state the type split exists to hold.

Providers: OpenAI, Ollama, LM Studio

Codex is not locked to OpenAI's servers. Three crates carry provider knowledge: model-provider-info (what a provider is), model-provider (talking to one), and models-manager (which models exist and what they can do). There are also dedicated crates for two local runtimes: codex-rs/ollama and codex-rs/lmstudio.

That is what makes running a local model possible: point Codex at an OpenAI-compatible endpoint on localhost and the same WireApi::Responses path applies.

ModelInfo is the type that keeps this honest. Module 5 saw model_info.input_modalities deciding whether images survive into the prompt; the same struct carries the context window that compaction measures against, and the comp_hash that run_turn watches for changes. Capabilities are data, not assumptions.

Engineering · Capability data beats feature flags

The naive way to support many models is if model.starts_with("gpt-5") { ... } scattered through the code. Codex instead loads a description of each model — context window, modalities, whether it reasons — and branches on capabilities. Supporting a new model becomes a data change. You saw the same instinct in Module 4's macro table: describe the thing once, derive the behaviour.

Retries, rate limits, and errors

Model APIs fail constantly — rate limits, timeouts, overloaded servers, streams that die mid-sentence. The retry policy is four lines:

Exponential backoff with jitter — wait longer after each failure, and multiply by a random 0.9–1.1 so that a thousand clients knocked offline by the same outage don't return in lockstep and knock the server over again.

Rust · saturating_sub

attempt is an unsigned integer, so attempt - 1 when attempt is 0 would underflow — a panic in debug builds, a wrap to 18 quintillion in release. saturating_sub stops at zero instead. Rust makes you choose explicitly: saturating_, checked_ (returns Option), or wrapping_. Python's integers are arbitrary-precision so the question never arises; here, picking the wrong one is a real bug class.

Retrying is not a single mechanism. There is a dedicated codex-rs/core/src/responses_retry.rs, and compact.rs imports backoff too — summarisation is a model call and can fail like any other. Meanwhile ResponseEvent::SafetyBuffering and ModelVerifications are non-error conditions the server can report mid-stream that still need surfacing rather than retrying.

You can ask for one model and be served another. And token accounting is a negotiation: if the server counted reasoning tokens, the client must not count them again, or every context-window calculation drifts. Auth: ChatGPT sign-in vs API key

Codex accepts several kinds of credential, and the enum documents each:

The distinction between Chatgpt and ChatgptAuthTokens is the interesting one, and it is a direct consequence of Module 1's four front doors. When you run codex login, Codex owns the OAuth flow and refreshes tokens itself. When Codex is embedded in a host application that is already signed in — the desktop app, an IDE — that host supplies tokens and Codex must not try to manage them. Same agent, two ownership models.

The machinery lives in codex-rs/login (~11,000 lines) and codex-rs/chatgpt, with codex-rs/keyring-store for storing secrets in the OS keychain rather than a plaintext file. AuthManager is handed out by ThreadManager, so every thread in a process shares one credential store and one refresh cycle.

Refreshing an expired token takes a network round trip. Doing it lazily means your first message pays for it; prewarm_auth moves that cost to startup, alongside prewarm_websocket and preconnect_websocket. A recurring theme in this file: do the slow thing before the user is waiting.

Careful

Which auth mode you use changes more than billing. Rate limits, available models, and which service tiers you may request all differ between a ChatGPT subscription and an API key. If you are reading this code to debug "why does it work for me and not for them", AuthMode is the first thing to check.

What is responses-api-proxy for?

Module 1's subcommand list included a hidden ResponsesApiProxy, and there is a codex-rs/responses-api-proxy crate. It lets a process that is not Codex make Responses API calls through Codex's credentials and network policy — useful when a sandboxed child needs model access without being handed a raw key. It reappears in Module 8, because "the sandbox blocks the network, but this one endpoint must work" is exactly the kind of hole that needs a guarded door rather than an exception.

What you now know

ModelClient is shared and ModelClientSession is per-turn so transport decisions survive retries. There is one wire API — the item-based Responses API — behind an enum kept as a seam. ResponseEvent streams everything including tool-call arguments, and end_turn may be absent, which is why the agent loop has fallback logic. Providers and model capabilities are data, so local models work through the same path. Failures get exponentially backed off with jitter, and the server can override your model choice and your token accounting. Auth has four modes because Codex is sometimes the host and sometimes the guest.
