Orientation

Before reading any code, you need a map: what Codex is as a product, how a repository of 126 crates and 1.2 million lines of Rust is laid out, why one executable behaves like a dozen different programs, and how the project stops itself from breaking. This module is that map.

What Codex actually is

Codex is a coding agent from OpenAI that runs on your own machine. You type a request in your terminal; a language model reads your files, proposes edits, and runs commands — with your approval, inside a sandbox. LLM · What makes it an agent

A plain chat completion returns text and stops. An agent runs a loop: send the conversation to the model; if the model replies with a request to call a tool ("run cargo test", "read src/main.rs"), execute that request, append the result to the conversation, and send it again. Repeat until the model replies with prose instead of a tool call. That loop is perhaps 200 lines of the 1.2 million in this repository. Nearly everything else exists to make those 200 lines safe, fast, resumable, and observable.

Those event names — turn/started, item/agentMessage/delta, item/completed, turn/completed — are not an SDK invention. They are the wire protocol of the Rust core, which we meet properly in Module 4. You have already seen the system's public vocabulary; the rest of the course is about what happens underneath it.

Engineering · Why so many crates?

In Python you would write this as one package with many modules, and any module could import any other. A Rust workspace splits code into crates — separately compiled units that must declare their dependencies explicitly in a Cargo.toml. That costs ceremony, and buys three things. Compilation is parallel and incremental, so touching the TUI doesn't rebuild the sandbox. Dependencies are a declared, acyclic graph rather than an accident, so "what does this depend on?" has a real answer. And a crate boundary is a genuine API boundary: items are private unless exported, which is why AGENTS.md says "Prefer private modules and explicitly exported public crate API."

Run codex and you get an interactive terminal session. But that same executable is also a script runner, an MCP server, a JSON-RPC daemon, a sandbox tool, a login helper, and a debugging harness. Here is a slice of the subcommand list:

Rust · Attributes and enum

The #[...] lines are attributes — metadata attached to the item below them, closest to a Python decorator. #[derive(clap::Subcommand)] asks the clap library to generate an argument parser from this type at compile time, so this enum is the CLI specification. #[cfg(...)] is conditional compilation: the App variant does not exist at all on Linux. And a Rust enum is not Python's Enum — each variant can carry different data (Exec carries an ExecCli, Update carries nothing). Module 2 covers this properly; it is the single most important Rust construct for reading this codebase.

Note the doc comments. In Rust, /// above an item is documentation, and clap lifts those strings straight into codex --help. The help text you see in your terminal is the source you are reading.

The arg0 trick

There is a subtler multiplexing going on. Codex ships as a single executable, but internally it needs to invoke a separate sandbox helper program. Rather than shipping two binaries, it checks the name it was invoked under:

OS · What "arg0" means

When any program starts, the operating system hands it a list of arguments, and slot zero is the name it was invoked as — not the file on disk. In Python that's sys.argv[0]. Because a hard link lets one file on disk have several names, a program can look at argv[0] and behave like a completely different tool. BusyBox famously packs a hundred Unix utilities into one binary this way. Codex uses it for exactly one thing: when invoked as codex-linux-sandbox, become the sandbox helper instead of the agent.

The stack-size detail in step 2 is real engineering scar tissue. Runtime::block_on runs the top-level future on whatever stack the OS gave main, which is often smaller than a Tokio worker's. Deeply nested async state machines overflowed it, so Codex spawns a thread with an explicit 8 MiB stack and runs everything there. You will find comments like this all over the repo; they are the best kind of documentation.

The layered architecture

Crate dependencies are declared, so the architecture is not a matter of opinion — you can read it out of the Cargo.toml files. Here is the spine, from the bottom up:

The load-bearing observation is that the front doors do not depend on each other, and core does not depend on any of them. core has no idea whether a human, an IDE, or a Python script is driving it. That is why the same agent can be four products.

Careful

The obvious guess about that diagram is wrong, and it is worth correcting now. You would expect the terminal UI to call core directly — same process, why not? It doesn't. Search the entire tui crate for CodexThread, core's main handle, and you get zero hits. The TUI talks to an AppServerClient, exactly like the IDE extension does.

That two-variant enum is the whole trick. InProcess runs the server as a task inside the same process — no sockets, no serialisation, just channels. Remote talks to a separate codex app-server process. Callers are written against one interface and cannot tell which they got, which means the terminal UI and the VS Code extension exercise the same code path. There is no "local shortcut" that could quietly drift and break only for IDE users. Module 10 returns to this in depth.

You can see the layering in the dependency lists themselves. Both core and tui depend on codex-protocol, codex-config, codex-login, and codex-sandboxing — shared foundations. But only core depends on codex-apply-patch, codex-execpolicy, and codex-rmcp-client, because only core executes tools:

Engineering · Read the Cargo.toml first

This is a technique worth stealing. When you meet an unfamiliar Rust crate, open its Cargo.toml before any .rs file. The dependency list tells you what the crate is allowed to do. A crate that doesn't depend on reqwest cannot make network calls; one that doesn't depend on codex-protocol isn't part of the agent conversation. It's a 30-second read that saves an hour of grepping. Python has no equivalent — any module can import anything at runtime.

There is one wrinkle worth flagging now so it doesn't surprise you later: tui also depends on codex-app-server-client and codex-app-server-protocol. The terminal UI does not always call core directly in-process; it can speak the same JSON-RPC protocol the IDE uses. Module 10 unpicks why.

How the project keeps itself honest

A codebase this size, changing this fast, with the power to run arbitrary commands on your machine, needs strong guardrails. Codex leans on four.

1. Tests, and a lot of them

1,158 files under codex-rs/ contain test functions, and there are 664 snapshot files on disk. In Rust, tests usually live in the same file as the code they test, at the bottom, behind an attribute:

#[cfg(test)] means this module is compiled only when running tests, so it costs nothing in the shipped binary. #[tokio::test] is for async tests — it builds a runtime around the test body. Codex also pulls large test suites into sibling files such as codex-rs/core/src/exec_policy_tests.rs; when you meet a *_tests.rs file, that is what it is.

Engineering · Snapshot testing

664 .snap files come from insta, a snapshot testing library. Instead of writing an expected value by hand, you assert that some output matches a stored file. First run, the file is created; on later runs, any difference fails the test and shows a diff you accept or reject. This is how you test something like a terminal UI, where the "expected value" is forty lines of styled text nobody wants to type into a test. Python's closest equivalent is pytest-regressions or syrupy.

Rust · Why holding a lock across await is a bug

await is a point where your task can be suspended and the thread goes off to run something else. If you are holding a mutex when that happens, you keep holding it while suspended — potentially for a network round trip — and every other task that wants it stalls. Worse, if the task you're waiting on needs that same lock, you deadlock. This is a classic async mistake in every language; Codex makes it a compile-time lint. Module 2 covers await.

3. A pinned toolchain

Every contributor and every CI machine compiles with the same Rust version, chosen deliberately rather than "whatever was installed". If you clone this repo, rustup reads this file and fetches 1.95.0 for you.

4. AGENTS.md — rules for the robots

The first rule explains a naming quirk you will trip over constantly: the directory is core/ but the crate is codex-core, and in Rust source the underscore form codex_core is what you use. Three names for one thing. Module 2 explains the underscore/hyphen conversion.

The sandbox rule is a genuine hazard sign. Codex is developed using Codex, inside its own sandbox, so parts of the test suite detect that they are sandboxed and skip themselves. An agent that "helpfully" cleaned up those checks would silently disable tests. Module 8 returns to this.

Why is there a Bazel build as well as Cargo?

Cargo is Rust's native build tool and is what you will use locally (just codex runs cargo run). Bazel is a language-agnostic build system with aggressive caching and remote execution — it can distribute a build across a fleet and reuse artifacts across machines, which matters when a full build is a million lines of Rust plus TypeScript plus Python. The cost is that both must be kept in sync, which is why AGENTS.md says changing Cargo.toml requires running just bazel-lock-update. You can ignore Bazel entirely for this course.

What you now know

Codex is one agent behind four front doors; the repository is a 126-crate Cargo workspace where core and tui are a third of the code; one binary multiplexes a dozen tools via subcommands and the arg0 trick; dependencies are declared, so the architecture is readable from Cargo.toml files; and the project defends itself with tests, snapshots, an opinionated linter, a pinned toolchain, and a rulebook for AI contributors.
