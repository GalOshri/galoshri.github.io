One Message Through the System

You type "what does safety.rs do?" and press Enter. Codex reads the file, runs a command, and answers. This module follows that one message through every layer it touches. Nothing here is covered exhaustively — each section names the module that opens the box properly. Think of this as the map you will keep returning to.

The journey has more layers than you would guess, so here is the whole route before we walk it:

The single most important structural fact — the one that explains the shape of the whole system — is that this is not a function call. Your message does not travel down a call stack and return with an answer. It is submitted to a queue, and results arrive later as a stream of events on a different queue.

Engineering · Why queues instead of calls?

Because a turn can take four minutes, and during those four minutes you must still be able to see progress, interrupt, or type a follow-up. A function call gives you one return value at the end and nothing in between. Two queues give you a running commentary and a channel to talk back. The price is that control flow stops being obvious — you can't just read down the page — which is exactly why this module exists.

The two ends of that pattern are a matched pair of tiny structs. Notice that both carry an id, and that the event's id is explicitly documented as pointing back at a submission:

From argv to a Config

Before any of that, the process has to start. Module 1 showed main handing straight to arg0_dispatch_or_else, which builds a Tokio runtime and calls cli_main. That function's first act is to destructure the parsed command line:

Rust · Destructuring in a let

let MultitoolCli { a, b, .. } = value; pulls fields out of a struct into local variables in one statement — Python's tuple unpacking, generalised to named fields. mut on individual bindings marks just those as mutable. It reads oddly at first, but it is everywhere in this codebase, and it is how a function announces exactly which parts of a big struct it intends to touch.

Because you ran codex with no subcommand, subcommand is None and the interactive field — a TuiCli — carries your prompt. Those raw arguments then become a Config, which is the single object describing everything about this run: which model, which approval policy, which sandbox, which working directory, which MCP servers.

Config is assembled from layers — built-in defaults, then ~/.codex/config.toml, then a named profile, then -c key=value overrides from the command line, then feature toggles. That layering is intricate enough to be its own subject; Module 11 covers it. For now, the only thing you need is that by the time anything interesting happens, there is one Config, and it is immutable.

Building the turn

A submission arrives, and the session spawns a task to handle it. Tasks are a small trait — this is the dependency-injection pattern from Module 2 again:

The directory listing of codex-rs/core/src/tasks tells you what kinds exist: regular.rs (an ordinary turn), compact.rs (summarise the conversation), review.rs (code review), user_shell.rs (you ran a shell command yourself). Yours is a regular turn.

Note cancellation_token in that signature. Every task is cancellable from birth, which is how Esc can stop a turn mid-flight — Module 5 follows it.

The very first thing a turn does is announce itself on the event queue. turn_id is ctx.sub_id — the submission id from earlier — so the UI can immediately tie this activity back to what you typed. The comment above it in the source explains the ordering choice: regular turns emit TurnStarted inline so the first turn's lifecycle doesn't wait on startup prewarming.

Everything arrives injected, and everything shared is an Arc — the session, the turn context, the extension data. This is the same "policy-free core" shape you would find in any well-built agent: run_turn owns almost no state, it orchestrates.

The conversation history is cloned and rendered for_prompt — filtered by what this model can actually accept (input_modalities: does it take images? audio?). This is the moment the internal representation becomes model input. Module 5 covers the context manager that decides what survives this step.

Rust · .instrument(trace_span!(...))

This wraps a future in a named tracing span, so logs and telemetry emitted anywhere inside it are attributed to run_turn.prepare_sampling_request_input. It is the async answer to "which part of the request was slow?" — and you will see it scattered through core. It has no effect on program logic; mentally skip over it.

There it is: the agent loop. Call the model. If the result needs following up — because the model asked to run a tool — go round again. Otherwise stop. Every agent ever written has this shape; the other 400 lines of run_turn are the things that make it survivable in production.

LLM · "Sampling" means calling the model

run_sampling_request looks like statistics jargon, and it is — generating text from a language model is sampling tokens from a probability distribution. Read sampling request as one API call to the model. A single turn may make many of them: one to decide to read a file, one after seeing the file, one after running a test.

Notice cancellation_token.child_token(). Each model call gets a token descended from the turn's, so cancelling the turn cancels the in-flight HTTP request too, rather than waiting politely for it to finish.

Notice also has_pending_input. If you typed something while the model was working, that alone forces another iteration — your interjection becomes part of the conversation before the turn is allowed to end. That is "steering", and it is why the loop condition is an || rather than just asking the model.

What run_sampling_request does — building the HTTP request to the Responses API, streaming server-sent events back, turning them into EventMsgs, retrying on rate limits — is Module 6.

Those four names are the entire life of a command, as seen from outside: permission asked, started, output streaming, finished. ExecCommandOutputDelta is why you watch test output scroll by live rather than waiting for a wall of text — the same streaming discipline as the model's own tokens.

You approve. The command runs inside the sandbox. Its output is captured, truncated if enormous, and appended to the conversation as a tool result. needs_follow_up is true, so the loop goes round again, and the model — now able to see the search results — writes its answer.

Careful

It is tempting to think of the sandbox as a setting. It is not: it is a different execution mechanism per platform — Seatbelt on macOS, Landlock and seccomp on Linux, a restricted token on Windows — each with different capabilities and failure modes. The reason SafetyCheck::AutoApprove is forced to carry a sandbox_type is so that this choice can never be left implicit.

The paper trail

Every event on that queue goes to two places: your screen, and a file.

The screen path is a loop that would be recognisable in any language. Here it is in codex exec, which is far easier to read than the TUI because it has no rendering to do:

Rust · tokio::select!

Waits on several futures at once and proceeds with whichever finishes first, cancelling the others. Here it races "the user pressed Ctrl-C" against "the agent sent an event". Python's nearest equivalent is asyncio.wait(..., return_when=FIRST_COMPLETED), but select! is a language-level construct and the losing branches are genuinely dropped. Note the , if interrupt_channel_open guard — a branch can be disabled by a condition.

Notice the two-way nature: ServerRequest means the agent is asking the client something — that is how an approval prompt reaches you. It isn't a pure event stream; it is a conversation between two peers.

What you now know

Your message became a ClientRequest to an in-process app-server, then an Op::UserInput on a submission queue. A RegularTask spawned, announced TurnStarted, rendered the history for the model, and entered a loop: call the model, and if it wants a tool, judge the tool with SafetyCheck, run it in a sandbox, feed the result back, loop again. Everything the turn did streamed out as Events, which reached your terminal and a rollout file at the same time.

That is the whole system in one pass. From here the course stops moving and starts digging — beginning with the vocabulary all of this is written in.
