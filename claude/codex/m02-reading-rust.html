Reading Rust When You Know Python

This module has one job: make every later excerpt readable. It is not a Rust course — you will not learn to write Rust here, and several famously hard topics are deliberately skipped. Every example is real code from Codex, so by the end you will have already read parts of the agent.

Structs, enums, and the compiler as pair programmer

Start with the single most important sentence: Rust checks types before your program runs, and refuses to compile if they don't line up. Python checks when it gets there, if at all. This changes how you read code — a Rust type signature is a promise the compiler has already verified, not a hopeful annotation.

Enums are the good part

This is where Rust departs sharply from Python, and it is the construct you will meet most often in this codebase. A Rust enum is a choice between alternatives, where each alternative can carry its own data. Here is the real security decision Codex makes before running anything:

A SafetyCheck is exactly one of three things. If it is AutoApprove it carries which sandbox to use and whether you approved explicitly. If it is Reject it carries a reason string. If it is AskUser it carries nothing, because nothing else is needed.

Rust · Why this beats the Python version

In Python you would probably return a dict — {"decision": "reject", "reason": "..."} — or a tuple, or three classes with a common base. All of them share a flaw: nothing stops you reading reason on an approval, or forgetting that "ask" is a possibility. With a Rust enum, the reason field does not exist unless the value is a Reject, and the compiler will not let you ignore a case. Making illegal states unrepresentable is the whole game, and it is why this codebase has so many enums.

match: the exhaustive switch

You read an enum by matching on it. This is Python's match statement, except the compiler counts the cases and errors if you missed one:

The | groups several variants into one arm. The _ inside Granular(_) means "it carries something; I don't care what." Now recall the rule from AGENTS.md in Module 1: "When possible, make match statements exhaustive and avoid wildcard arms." That rule is a safety mechanism. If someone adds a fifth approval mode tomorrow, every exhaustive match in the codebase stops compiling until a human decides what the new mode should do. A wildcard _ => {} arm would silently swallow it — and in a file called safety.rs, silently defaulting is how you get a security bug.

Ownership and borrowing

This is the one genuinely new idea, and the reason Rust exists. The good news for a reader: you mostly need to recognise three symbols, not to reason like a compiler.

In Python, every variable is a reference to an object, and a garbage collector frees objects once nothing points at them. Rust has no garbage collector. Instead, every value has exactly one owner, and when the owner goes out of scope the value is freed. That would be unbearably restrictive on its own, so you can borrow a value instead of taking ownership — that's what & means.

Read that signature as a set of promises:

SyntaxMeansPython intuition
&TBorrowed, read-only. The caller keeps ownership; this function may look but not modify.Passing an object you promise to treat as immutable
&mut TBorrowed, exclusive. May modify; nobody else may touch it meanwhile.Passing a list you intend to mutate
TOwned, moved in. The caller gives it up entirely.Handing over the only copy

So assess_patch_safety borrows the patch, the profile, the policy and the directory — it will read them and give them back untouched — while policy and windows_sandbox_level are passed by value because they are small Copy types (remember #[derive(..., Copy, ...)] on AskForApproval), so copying is cheaper than referencing.

Rust · The rule that buys everything

At any moment a value may have either any number of & readers or exactly one &mut writer — never both. That single rule, checked at compile time, is why Rust has no data races and no use-after-free. It's also why the compiler sometimes rejects programs that would have been fine; that frustration is a writer's problem, not a reader's. As a reader, just note who is allowed to mutate what.

Rust · Arc<T>, when one owner isn't enough

Sometimes several parts of the program genuinely need to share one value — the config, say, or a connection to the model. Arc<T> ("atomically reference counted") is the escape hatch: it wraps a value and counts how many holders exist, freeing it when the count hits zero. This is precisely how every Python object works, so when you see Arc<Config>, read it as "a normal Python object reference" and move on. The A means the counting is thread-safe, which matters because Codex is heavily concurrent.

Go deeper (optional)

Lifetimes — the 'a in TimeFuture<'a> — are the compiler's way of proving a borrow doesn't outlive the thing it borrows from. You will see them in signatures throughout this codebase. For reading purposes you can treat 'a as noise and 'static as "lives forever". Nothing in this course depends on understanding them further.

Result, Option, and the ? operator

Rust has no exceptions. A function that can fail says so in its return type, and the caller cannot accidentally ignore it. Two enums carry the whole story — and now that you've read the last two sections, you can see they're just ordinary enums:

Option<T> is "a T, or nothing" — Python's T | None, except you cannot forget to check. Result<T, E> is "a T, or an error E" — the return value of anything that can fail.

The ? operator

Checking every Result by hand would be miserable, so Rust has one character for it. Recall main from Module 1:

cli_main(...).await? means: run it, and if it returned Err(e), return that error from the enclosing function immediately; otherwise unwrap the Ok value and carry on. It is Python's raise-propagation, made explicit at every call site.

Rust · Why ? is better than invisible exceptions

In Python, any line can raise, and you find out by reading documentation or by crashing in production. In Rust, a line that can fail is visibly marked. Scanning a function for ? tells you exactly where it can bail out. The flip side: a function with no ? and no Result in its signature genuinely cannot fail, and you can stop worrying about it. That's information Python never gives you.

The Ok(()) at the end is idiomatic: () is the unit type, Rust's None-as-a-return-value, so Ok(()) reads "succeeded, no value to report".

Traits and generics

A trait is a set of method signatures a type can promise to provide. If you know Python's Protocol or abstract base classes, you already have the idea. Here is one small enough to read whole — the boundary Codex uses to ask "what time is it?":

Any type that provides current_time and sleep can be a TimeProvider. The : Send + Sync after the name adds two more requirements — those are themselves traits, meaning "safe to move between threads" and "safe to share between threads". You will see Send + Sync everywhere in this codebase; read it as "usable from Codex's many concurrent tasks".

Implementing a trait is a separate block, which is the biggest structural difference from Python classes:

Three things to collect. struct SystemTimeProvider; with no fields is a type that exists purely to have methods hung on it. The leading underscore in _thread_id tells the compiler "I know I'm not using this parameter, don't warn me" — the real system clock doesn't care which thread is asking, but the trait requires the parameter because other implementations will. And pub(crate) means public within this crate only.

Why bother? Because it makes time fake-able

You can now read this line by line, and it uses everything from this module. Arc<dyn TimeProvider> is the key phrase: dyn Trait means "some type implementing this trait, decided at runtime" — which is what every Python object reference is. config.map(...) applies a function only if the Option has a value; .unwrap_or_default() supplies the default otherwise. The match is exhaustive over the two clock sources. .ok_or_else(...) converts "no external provider was supplied" from a None into a Result error with a helpful message.

Engineering · Why an interface for the clock?

Because a test that calls the real clock is a test that is slow and flaky. With TimeProvider behind a trait, a test injects a fake that jumps forward an hour instantly. This is dependency injection, and you will see the same pattern for the model client, the filesystem, and the sandbox — every boundary where Codex touches the outside world is a trait, precisely so it can be faked. When you meet an unfamiliar trait in this codebase, "what does this let them fake in tests?" is usually the right question.

Generics: <T> and where it differs from Python

Option<T> and Result<T, E> are generic: T is a placeholder for a type filled in at each use site. Python has the same notation in type hints (Optional[str]), but there it is documentation the runtime ignores. In Rust the compiler generates a separate specialised copy of the code for each concrete T, so generics cost nothing at runtime. That's why the codebase uses them freely.

The trade-off is against dyn Trait: generics are resolved at compile time and are faster; dyn is resolved at runtime and is more flexible. Arc<dyn TimeProvider> uses dyn because the choice genuinely isn't known until the config is read.

async, tokio, and channels

Codex spends most of its life waiting — for the network, for a subprocess, for you. Async is how it waits for many things at once without a thread for each. If you've used Python's asyncio, this will feel familiar; the shapes are nearly identical.

RustPythonMeaning

f().awaitawait f()Run it; yield to other tasks while waiting

One real difference matters for reading. In Python a coroutine starts running as soon as you await it and the event loop is implicit and global. In Rust a Future is completely inert until something polls it, and the runtime is an ordinary library you construct yourself. That's why Module 1's arg0_dispatch_or_else had to "construct a Tokio multi-thread runtime" as an explicit step — there is no runtime unless someone builds one.

Rust · What async move means

async { ... } creates a future from a block. move tells the closure to take ownership of the variables it mentions, rather than borrowing them. It's required here because the future will outlive the function that created it — it gets handed to the runtime and run later, by which time the original scope is gone. When you see async move, read "package this work up, taking everything it needs with it."

And Box::pin, from SystemTimeProvider above: a future is a state machine whose size depends on its contents, so a trait method that returns "some future" must put it behind a pointer. Channels: how concurrent parts talk

Codex is built out of independent tasks that pass messages, not out of shared mutable state. The tool for that is a channel — a queue with a sending end and a receiving end:

mpsc is "multi-producer, single-consumer": many senders, one receiver. The 64 is the buffer size — if the receiver falls behind, senders wait, which is backpressure for free. while let Some(event) = rx.recv().await loops until the channel closes and recv returns None. Python's closest equivalent is asyncio.Queue.

This one pattern is the backbone of the whole system. Module 4 shows that Codex's core protocol is literally two queues — you submit operations on one and receive events on the other — and Module 5 shows the agent loop draining them.

What you now know

Structs are dataclasses; enums are tagged choices that make illegal states unrepresentable; match is exhaustive by policy; & borrows and bare types move; Result plus ? replaces exceptions with visible, checked failure; traits are interfaces that exist so boundaries can be faked in tests; and async looks like asyncio with an explicit runtime and inert futures.

That is the whole toolkit. Anything else you meet — a macro, a lifetime, an exotic generic bound — will be explained in a concept box where it appears. Next we spend a module doing nothing but following a single message through the entire system, which turns this vocabulary into a map.
