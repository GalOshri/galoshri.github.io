Tools — Giving the Model Hands

A language model can only emit text. Everything else — reading your files, running your tests, editing your code — happens because Codex offers it a menu of functions and executes whichever it picks. This module is that menu: how tools are declared, dispatched, and executed, and why the edit format is a bespoke diff dialect with its own grammar file.

LLM · Why tool_search exists

Every tool definition costs tokens in every request, forever. Twenty tools with detailed schemas can be thousands of tokens before you have said anything. tool_search inverts this: expose a handful of tools plus a way to look up the rest on demand. The deferred_tool_namespaces method on the registry is the other half of that mechanism. It is the same instinct as compaction in Module 5 — context is the scarce resource.

OS · Why Windows needs a longer floor

Process creation on Windows is substantially more expensive than fork/exec on Unix, and console handling differs. A 250 ms yield that works fine on macOS would, on Windows, routinely return "still running" for commands that were about to finish. Rather than pick one number and be wrong somewhere, Codex tells the model different truths on different platforms.

yield_time_ms also reveals the shell tool's real design. It does not block until a command finishes — it waits a while, and if the command is still running, returns a session id. That is what makes long-running processes possible: npm run dev keeps running, the model gets a handle, and Module 5's list_background_terminals and terminate_background_terminal on CodexThread exist to manage the result.

max_output_tokens is the other guard: "Output token budget. Defaults to 10000 tokens; larger requests may be capped by policy." A single cat of a large log could otherwise blow the entire context window in one tool call.

apply_patch: the edit format

Codex does not let the model write files directly, and it does not use git diff format. It defines its own patch dialect — and, unusually, ships a formal grammar for it:

Seventeen lines that define the entire edit language. A patch is a Begin/End envelope containing hunks; each hunk adds, deletes, or updates one file; an update may rename; changed lines are prefixed +, -, or space.

Engineering · Why not unified diff?

A git unified diff identifies edits by line numbers (@@ -42,7 +42,9 @@). A model cannot reliably count lines, and if it is off by two, the patch either fails or — worse — applies in the wrong place. Codex's format identifies edits by surrounding context instead: show me three lines either side and I will find them. That is a format designed around what language models are good at, and it is one of the more consequential design decisions in the product.

The model learns this format from a prompt template that is shipped as Markdown and embedded with include_str!:

The @@ class BaseClass mechanism is the escape hatch for repeated code: name the enclosing scope, and stack several @@ lines to narrow further. It is addressing-by-description rather than by position.

The self-invocation trick

This is Module 1's arg0 trick again. Codex can re-run itself as a patch applier, which means the edit happens in a separate process that can be sandboxed exactly like any other command. The doc comment even explains why the constant lives in this crate — to avoid a dependency cycle. That is the Cargo.toml-shaped thinking from Module 1 showing up in a single constant's placement.

Reading, planning, searching

Notably absent from the handler list is a read_file tool. Codex generally has the model use the shell — cat, sed, rg — rather than providing a bespoke reader. Fewer tools, less schema in every request, and the model already knows Unix.

What does get dedicated tools is anything the shell cannot express. Three categories are worth calling out.

Tools that talk to you. request_user_input and request_permissions let the model ask a question mid-turn. These are what produce the ServerRequest messages you saw the codex exec loop handle in Module 3 — the agent asking the client, rather than the other way round.

Tools for self-management. get_context_remaining lets the model ask how much room it has left; new_context_window lets it start fresh. Compaction in Module 5 is Codex deciding to forget; these are the model deciding.

Tools that spawn agents. codex-rs/core/src/tools/handlers/multi_agents.rs and its _v2 successor let a turn delegate to sub-agents. The TurnItem enum in Module 4 had matching entries — SubAgentActivity, CollabAgentToolCall — so a sub-agent's work appears in your transcript rather than vanishing.

Two renderings of one result: into_response produces a conversation item to send back to the model; code_mode_result produces JSON for code mode, an alternative where the model writes a script that calls tools rather than emitting one call at a time. Hence the codex-rs/code-mode crates.

LLM · What MCP is

The Model Context Protocol is a standard by which a program exposes tools and resources to an AI agent. You configure an MCP server — a database client, a ticket tracker, a browser — and its tools appear alongside Codex's own. It is a plugin protocol for agents, deliberately vendor-neutral, and Codex both consumes it and provides it (Module 10).

The design decision worth noticing is that MCP tools are not a special case at the point of use. They arrive through the same registry, are dispatched through the same router, produce McpToolCallBegin/End events shaped like every other operation, and land as TurnItem::McpToolCall. The model cannot tell the difference.

What makes it hard is everything around that. Servers are external processes that start slowly, crash, change their tool list at runtime, or return enormous results — which is why there is a whole cluster of supporting files:

Engineering · The distance from a toy agent

A tutorial agent's tool call is: parse JSON, call the function, stringify the result. Codex's is: parse, match to a registry entry that may not exist, decide whether it may run at all, ask the user if not, choose a sandbox, decide whether it can run in parallel with its siblings, execute with streaming output and cancellation, truncate to a token budget, emit lifecycle events, record telemetry, and render the result twice for two consumers. Each step is one of those files. This is what "production" means, and it is why the ratio of loop to scaffolding is what it is.

What you now know

Tools implement CoreToolRuntime, whose default methods mark what varies; the registry is assembled per turn and holds Arc<dyn …> handlers. Tool schemas are built in code so their descriptions — which are prompt, not documentation — can differ per platform. The shell tool yields a session id rather than blocking, which is how background processes exist. apply_patch is a context-addressed diff dialect with a 17-line grammar, a streaming parser, and a self-invoking standalone mode. MCP tools are deliberately indistinguishable from built-ins at the point of use, and pay for it in supporting machinery.

Every one of those tool calls has been quietly deferring one question: is it safe to run this? That is the next module.
