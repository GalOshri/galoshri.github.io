tui/ — The Terminal Interface

At ~200,000 lines across 134 top-level entries, tui is the largest crate in the repository — bigger than the agent it drives. That ratio is not a mistake. Everything you have read so far is invisible; this is the only part anyone sees, and a terminal gives you nothing for free.

ratatui and the app shell

Codex builds on ratatui, the standard Rust library for terminal UIs. Ratatui is immediate-mode: you do not create widget objects that persist, you re-describe the entire screen every frame and the library works out which characters changed.

Terminal · What you actually control

A terminal is a grid of cells, each holding one character plus attributes (bold, dim, a colour index). You change it by writing escape sequences — \x1b[2J clears, \x1b[10;5H moves the cursor. There are no widgets, no layout engine, no event objects, and no pixels. Anything that looks like a scrollable transcript with a text box at the bottom was built by someone, by hand, out of characters.

Codex does not use ratatui's terminal wrapper unmodified. It forked it:

Vendoring a dependency's core type is a serious decision, and the reason is Codex's most distinctive UI behaviour: it does not take over your whole terminal. Conversation history scrolls into your real scrollback, where you can select it, copy it, and still see it after Codex exits. Only the bottom few lines are managed. Standard full-screen terminal apps use an "alternate screen" that vanishes on exit; keeping the transcript in normal scrollback while still drawing a live UI below it requires cursor and viewport control that ratatui's Terminal does not expose.

The event loop

A terminal app is a loop over events from several sources at once: your keystrokes, the agent's notifications, terminal resizes, timers. AppEvent is the union of everything that can wake the UI:

Notice that almost every variant carries a ThreadId. The TUI is not a single-conversation program — it manages several threads at once, with a picker to switch between them, and "submit to this thread regardless of current focus" as an explicit capability. Module 5's ThreadManager exists because of screens like this.

RetrySafetyBufferedTurn is a good example of how much product logic lives up here. Recall ResponseEvent::SafetyBuffering from Module 6 — the server withholding output pending a check. The UI's response is a compound operation: interrupt the turn, fork the thread so the original is preserved, and retry with the model the server suggested. Three core operations behind one user gesture.

Engineering · Why an event enum rather than callbacks

Every asynchronous source — keyboard, agent, timer — converts its input into one AppEvent and pushes it onto a channel. One loop drains that channel and mutates state in one place. This is the same submission-queue discipline as Op in Module 4, and it buys the same thing: ordering is well-defined, state changes are serialised, and the whole application can be tested by feeding it a list of events. It is why app_event_sender.rs exists as its own module — the sending half is handed out to anything that needs to speak.

The chat transcript

chatwidget — a file and a directory — owns the conversation view. Its job is to turn the event stream from Module 4 into rendered cells, incrementally, while text is still arriving.

The hard part is that terminal rendering is line-based and streaming text is not. A Markdown code fence is only recognisable once you have seen its closing backticks, but you must display something now. Hence the neighbouring modules: markdown.rs, markdown_stream.rs, markdown_render.rs, streaming, and live_wrap.rs.

Diffs get their own pipeline too — diff_render.rs, diff_model.rs, get_git_diff.rs — because Module 7's apply_patch results need to be shown as coloured diffs, and the streaming parser means they can be shown while the model is still writing them.

Command output has a dedicated exec_cell module: a command that runs for two minutes and prints ten thousand lines cannot simply be appended, so it is rendered as a collapsible cell that fills in live. That is the ExecCommandBegin/OutputDelta/End triple from Module 4 arriving at its destination.

Go deeper (optional)

ascii_animation.rs, frames.rs, and shimmer.rs are the spinner and the "thinking" shimmer. They look like frivolity in a codebase this serious, but a turn can run for minutes and an interface that appears frozen is a bug report. Feedback under latency is a feature.

The composer

bottom_pane/ is where you type, and it is the densest part of the crate — dense enough that it has its own AGENTS.md:

Writing a text editor is genuinely hard, and a terminal one is harder. Cursor movement through wrapped lines, multi-line input where Enter sometimes submits and sometimes inserts a newline, history you can scroll back through, paste of a hundred lines arriving as a hundred keystrokes, and Unicode where one character can be two cells wide.

chat_composer_history.rs is worth singling out. Shell-style history sounds trivial until you consider that you may have edited the current draft before pressing Up — so the draft has to be preserved, restored on the way back down, and not confused with a recalled entry.

command_popup.rs is slash-command completion. Typing / opens a filtered list — the same interaction as an IDE autocomplete, implemented from scratch over a character grid. Alongside it, file_search.rs backs @-mentions of files, powered by the codex-rs/file-search crate.

And external_editor.rs is the humane escape hatch: give up, open $EDITOR, read the file back when it exits.

Approvals and diffs

Module 8 ended with SafetyCheck::AskUser and an event going out on the queue. approval_overlay.rs is where that lands.

This is the highest-stakes UI in the product. The user is making a security decision, usually quickly, often repeatedly, and the interface has to convey enough for that decision to be meaningful — what command, in which directory, with what sandbox, and why approval is being requested at all. The supporting files (approval_events.rs, app_server_approval_conversions.rs, auto_review_denials.rs) exist because an approval is not one message but a small protocol: request, decision, remembered scope, and what happens to the queued work if you say no.

Engineering · Approval fatigue is a security bug

If a tool asks fifty times an hour, users stop reading and approve reflexively — at which point the prompt provides no protection while still costing attention. That is why Module 8's design puts so much weight on not needing to ask: a good sandbox means auto-approval is safe, and every avoided prompt makes the remaining ones more likely to be read. The granular approval config exists so you can turn off whole categories you have decided you do not want to be asked about.

Terminal · Why ANSI colours, not RGB

The sixteen ANSI colours are names, not values — red means "whatever this user's theme calls red". Every terminal theme is designed so those sixteen are legible against its background. A hard-coded #1a1a1a looks right in exactly one theme and becomes invisible in others. Deferring to the user's palette is both an accessibility choice and the only way to look correct everywhere.

onboarding/ handles first run: sign-in, trusting a directory, choosing an approval mode. It is also where the two-front-doors design from Module 6 surfaces — the flow differs depending on whether Codex owns your credentials or a host application supplied them.

The migration modules are an unusual find: external_agent_config_migration*.rs, five files, plus the codex-rs/external-agent-migration crate (~14,000 lines). This is machinery for importing configuration from competing coding agents. Nothing about it is technically deep; it is here because it tells you what the product is trying to be.

What you now know

tui is larger than the agent because terminals give you a character grid and nothing else. Codex vendored ratatui's Terminal so the transcript can live in your real scrollback instead of an alternate screen. One AppEvent enum funnels every input source into a single loop, with thread ids on almost every variant because the UI is multi-conversation. Streaming Markdown, live diffs, and collapsible command output each need their own pipeline. The composer is a hand-written text editor with history, completion, and an $EDITOR escape hatch. Approvals are the highest-stakes screen in the product. And a Markdown style guide, enforced by clippy.toml, keeps it legible in every terminal theme.

This was one front door. Next: all the others.
